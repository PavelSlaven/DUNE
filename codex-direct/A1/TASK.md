# Задание A1 — контракт графики юнитов

Режим: **«Ведёт sol»** (см. «Режимы задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/a1`. План работ проекта: `docs/PLAN_units_sega_upstream.md`, шаг А1.

## Цель

Создать детерминированный скрипт `tools/units3d/unit_contract.py`, который по пакам из `/srv/dune/inputs/packs/` и исходникам движка строит `docs/units/unit_contract.json` и `docs/units/UNIT_CONTRACT.md`, и тест `tools/units3d/tests/test_unit_contract.py`, который доказывает, что оба файла совпадают с выводом скрипта и с паками.

## Зачем

Дальше юниты будут рендериться из 3D-моделей. Скрипт рендера и приёмочные проверки (`tools/units3d/check_unit.py`, задание A2b) берут из этого контракта размеры кадров, число столбцов и строк, угол поворота модели для каждого столбца, правила отрисовки и направление света. Ошибка в контракте — ошибка во всех атласах.

## Что входит в контракт

### 1. Записи

Все записи `sdl_data_hd4.dat`, имя которых начинается с `UNIT_` или `HM_UNIT_`. Для каждой записи — запись с тем же индексом в `sdl_data.dat` (классика). Пака HD2 нет: движок грузит только `*_hd4.dat` (`defaultHdDataFileName` в `src/cGame_logic.cpp`). Чтение паков — функциями `read_pack` и `decode_image` из `tools/hd_assets.py`.

Поля каждой записи в JSON:

| Поле | Значение | Источник истины |
|---|---|---|
| `index`, `name` | индекс и имя записи | пак HD4 |
| `role` | одно из: `body`, `top`, `shadow`, `mask_body`, `mask_top` | присваивания `sUnitInfo[...]` в `src/utils/cIniGameRessouces.cpp`; для масок — имя `HM_<имя атласа>` |
| `unit_types` | список констант типа юнита, которые используют запись (например, `TANK`) | `src/utils/cIniGameRessouces.cpp` |
| `hd4_size`, `classic_size` | `[ширина, высота]` изображения; `null`, если записи нет | паки |
| `frame_classic` | `[bmp_width, bmp_height]` юнита | место, где движок задаёт `bmp_width` и `bmp_height`; ссылка в поле `sources` |
| `frame_hd4` | `frame_classic × 4` | вычисление |
| `columns`, `rows` | целые: `hd4_size[0] // frame_hd4[0]` и `hd4_size[1] // frame_hd4[1]` | вычисление |
| `remainder_px` | `[hd4_size[0] − columns × frame_hd4[0], hd4_size[1] − rows × frame_hd4[1]]` — полосы справа и снизу, которые движок не читает | вычисление; правило чтения кадра — в `draw_rules` |
| `row_meaning` | что означает номер строки (`iFrame`) для этого юнита: например «одна строка», «кадры добычи харвестера» | код, который меняет `iFrame` для этого типа юнита; ссылка в `sources` |
| `column_meaning` | список длины `columns`, элемент — `{"column": <целое>, "direction": <"E", "NE", "N", "NW", "W", "SW", "S", "SE" или null>, "yaw_deg": <целое или null>}`; `yaw_deg` — поворот модели против часовой стрелки при взгляде сверху, 0 — нос на восток; `null`, если столбец не направление (тогда добавляется поле `"meaning"` с текстом) | `convertAngleToDrawIndex` и код отрисовки этого юнита; ссылка в `sources` |
| `facing_source` | `"iBodyFacing"`, `"iHeadFacing"` или `null` — какое поле юнита выбирает столбец | код отрисовки; ссылка в `sources` |
| `draw_sites` | список всех мест в `src/`, где движок рисует эту запись: `{"source": "<путь>:<строка>", "column": <как выбирается столбец>, "row": <как выбирается строка>}`; столбец и строка — числом, если постоянны, иначе текстом | поиск по `src/` всех обращений к записи (через функции `getUnit*Bitmap`, индекс или имя) |
| `painted_entry` | у масок — имя записи, которую маска красит; у остальных — `null` | пак HD4 |
| `house_mask` | имя записи `HM_` для этой записи или `null` | пак HD4 |
| `sega_reference` | путь `resources/hd/source_references/battle_for_arrakis_complete/<файл>` — Sega-лист, из которого построен HD4-атлас записи; никогда не `null` | список `UNITS` в `tools/build_review_asset_pack.py` (правило ниже) |
| `sources` | список ссылок `путь:строка` на каждое утверждение записи, взятое из кода | код |

Правило `sega_reference`. Атласы HD4 построены из Sega-листов сборщиком; таблица «атлас → лист» записана в списке `UNITS` файла `tools/build_review_asset_pack.py`: каждый элемент — вызов `AssetSpec(...)`, у которого поле `symbol` — имя атласа, поле `source_file` — имя файла листа. Скрипт разбирает этот файл модулем `ast` (без импорта): порядок позиционных аргументов — порядок полей класса `AssetSpec` в том же файле, именованные аргументы — по имени поля. Значение записи:
- `body` и `top` — `source_file` элемента `UNITS`, у которого `symbol` равен имени записи;
- `shadow` — значение записи с ролью `body` и тем же `unit_types`;
- `mask_body` и `mask_top` — значение записи `painted_entry`.

Каждый файл листа должен быть в `files` файла `resources/hd/source_references/battle_for_arrakis_complete/manifest.json`. Запись без значения, лист не из manifest или больше одной записи `body` с тем же `unit_types` — скрипт завершается ошибкой с именем записи, а ты присылаешь `Q`; `null` не пишется. Поля `sega_reference_note` нет. Ручной таблицы «тип → лист» в скрипте нет; разбор имён файлов manifest по подстрокам удалить.

Записи, у которых `hd4_size` не равен `classic_size × 4` (например, `UNIT_CARRYALL_SHADOW`: классика 400×112, HD4 1536×384) или `remainder_px` не равен `[0, 0]`, не исправлять, а перечислить в общем списке `size_exceptions`: `name`, `hd4_size`, `classic_size`, `frame_hd4`, `remainder_px`. Атласы пилота `UNIT_SIEGEBASE` (1152×152, кадр 144×144) и `UNIT_DEVASTATOR` (1216×192, кадр 152×184) — такие записи: размеры атласов остаются как в паке.

### 2. Правила отрисовки — общий раздел JSON `draw_rules`

Каждое правило — значение и ссылка `путь:строка`:
- где рисуется кадр юнита на экране — всю цепочку, каждое звено своей ссылкой: смещение `cUnit::draw_x` и `cUnit::draw_y` относительно клетки; как это смещение прибавляется к позиции юнита через камеру; что `cUnit::draw` рисует кадр в `getVisualRectangle()` — прямоугольник, масштабированный на `unitWorldScaleFactor` вокруг центра кадра, и чему этот множитель равен;
- что тень, корпус и башня рисуются в одном прямоугольнике и в каком порядке (`cUnit::draw`);
- какой участок атласа читается для кадра: `start_x`, `start_y` (`cUnit.cpp`), и что поэтому полосы `remainder_px` движок не читает;
- `direction_columns`: список из 8 элементов `{"column", "direction", "yaw_deg"}`, выведенный из `convertAngleToDrawIndex` и констант `FACE_*` с разобранными из кода значениями смещения и числа направлений;
- прозрачность тени (`ShadowTrans`: числовое значение) и особые смещения тени (например, у `CARRYALL` +24 по y, найденное внутри ветки `CARRYALL` функции `cUnit::draw`);
- как маска `HM_` окрашивает пиксели цветом Дома: при каком условии движок вообще идёт путём HD-текстур с масками, а при каком — палитровым путём без масок (`src/player/cPlayer.cpp`, присваивание `m_hdTextureReferences`); формула силы окраски, условие пропуска пикселя, условие пропуска всей маски и как выбирается имя маски (`src/utils/Graphics.cpp`, участок применения маски); что тени юнитов не окрашиваются — ссылкой на исполняемую строку `getUnitShadowBitmap`, а не на комментарий; каждое из этих утверждений — один раз, без повтора под другим ключом;
- размер клетки в классических пикселях (`TILESIZE_WIDTH_PIXELS`, `TILESIZE_HEIGHT_PIXELS`).

### 3. Направление света — раздел JSON `light`

Для каждой записи `BUILD_*_SHADOW` пака HD4, у которой есть запись здания без суффикса `_SHADOW`:
- размер кадра здания определить по коду движка (ссылка в `sources`); брать кадр 0;
- непрозрачные пиксели — пиксели с α > 16;
- вектор тени = центр масс пикселей тени, не закрытых зданием, минус центр масс пикселей здания; если код рисует тень здания со смещением, сначала применить это смещение;
- записать угол на экране в градусах (0° — вправо, 90° — вверх, то есть `atan2(-dy, dx)`), длину в пикселях HD4, `shadow_runtime_rendered` (рисует ли движок эту тень, со ссылкой) и число пикселей тени вне здания.

Итог раздела:
- список по зданиям;
- `median_angle_degrees` и `median_length_px` — медианы только по зданиям с `shadow_runtime_rendered: true`. `median_angle_degrees` — круговая медиана в определении `docs/units/UNITS3D_SPEC.md` §5 (её читает проверка 9 задания A2b): угол из набора, у которого сумма модулей разностей `((a − b + 180) mod 360) − 180` с остальными углами наименьшая; при равных суммах — угол здания, которое стоит раньше в списке зданий. `median_length_px` — обычная медиана (`statistics.median`). В `light.measurement` записать оба определения словами;
- у каждого здания `outlier: true`, если круговая разница его угла и медианы больше 45°, иначе `false` (в медиане выбросы остаются);
- список `excluded`: здания без записи тела, с пустой тенью, со смещением, которое скрипт не смог вычислить, и с тенью, которую движок не рисует, — у каждого причина.

### 4. Документ `docs/units/UNIT_CONTRACT.md`

Генерирует тот же скрипт из JSON; текст, написанный не скриптом, в документ не добавлять. Размер — не больше 40 000 байт. Дробные числа — с одним знаком после запятой. Состав:
- таблица записей: индекс, имя, роль, типы, HD4-атлас `Ш×В`, HD4-кадр `Ш×В`, `columns × rows`, `remainder_px` (если не `[0, 0]`), маска, имя файла Sega-листа (без пути);
- «Правила отрисовки»: каждое правило одной строкой, с 1–3 ссылками `путь:строка`;
- «Свет»: таблица зданий (угол, длина, рисует ли движок, выброс), медианы и список `excluded` с причинами.

Полные списки `sources`, `draw_sites`, центроиды, счётчики пикселей и параметры метода остаются только в JSON.

## Тест

`tools/units3d/tests/test_unit_contract.py` на `unittest` из стандартной библиотеки (pytest в окружении нет). Путь к пакам — переменная окружения `D2TM_PACK_DIR`; без неё тест пропускается с сообщением. Временные файлы теста — в `tempfile.TemporaryDirectory()`. Проверки:
1. Скрипт, запущенный во временную папку, выдаёт JSON и MD, побайтно равные закоммиченным.
2. Для каждой записи: `columns × frame_hd4[0] + remainder_px[0] == hd4_size[0]` и `rows × frame_hd4[1] + remainder_px[1] == hd4_size[1]`; запись с ненулевым `remainder_px` есть в `size_exceptions`. Известные случаи — значения записаны в самом тесте, не берутся из генератора: `UNIT_SIEGEBASE` — `hd4_size` `[1152, 152]`, `frame_hd4` `[144, 144]`, `remainder_px` `[0, 8]`, `columns` 8; `UNIT_DEVASTATOR` — `[1216, 192]`, `[152, 184]`, `[0, 8]`, 8.
3. Размер каждой записи `HM_` равен размеру записи из её `painted_entry`.
4. Каждая ссылка `путь:строка` из `sources`, `draw_sites` и `draw_rules` указывает на существующую строку файла, в этой строке есть идентификатор, на который ссылается правило (идентификатор хранится в ссылке рядом со строкой), и строка — не комментарий: после начальных пробелов она не начинается с `//` и не лежит внутри блока `/* … */`. Тот же отсев комментариев — в функции скрипта, которая ищет строку ссылки.
5. У каждой записи длина `column_meaning` равна `columns`. У каждой записи с `facing_source` не `null` все `direction` и все `yaw_deg` не `null`, а `yaw_deg == 45 × индекс направления в порядке E, NE, N, NW, W, SW, S, SE`. `draw_rules.direction_columns` совпадает с этим порядком.
6. У каждой записи `sega_reference` не `null`, файл существует и есть в `files` manifest. Известные случаи — значения записаны в самом тесте: `UNIT_LAUNCHER`, `UNIT_LAUNCHER_SHADOW`, `HM_UNIT_LAUNCHER` — `550380_missile_tank_deviator.png`; `UNIT_FRIGATE`, `UNIT_FRIGATE_SHADOW` — `550136_starport_ship.png`; `UNIT_SABOTEUR`, `HM_UNIT_SABOTEUR`, `UNIT_SINGLEFREMEN`, `HM_UNIT_SINGLEFREMEN`, `UNIT_TRIPLEFREMEN`, `HM_UNIT_TRIPLEFREMEN` — `169099_soldier_infantry.png`; `UNIT_SONICTANK` и `UNIT_SIEGEBASE` — `550030_siege_tank.png`; `UNIT_DEVASTATOR` — `550032_devastator.png`. Известный случай расходится с `UNITS` — `Q` с цитатой строки `tools/build_review_asset_pack.py`; тест не ослаблять.
7. `UNIT_CONTRACT.md`: размер не больше 40 000 байт; в таблице записей ровно одна строка на каждое имя из `entries` JSON и других строк записей нет; в разделах «Правила отрисовки» и «Свет» строк столько же, сколько правил в `draw_rules` и зданий в `light`.

Каждый новый или изменённый тест 2, 4–7 краснеет на мутации своего поля: копия JSON, где у всех записей `direction` = `null` (тест 5), `sega_reference` у `UNIT_LAUNCHER` = `null` (тест 6), ссылка ведёт на строку комментария (тест 4), MD пустой (тест 7), `frame_hd4` у `UNIT_SIEGEBASE` = `[144, 152]` (тест 2). Чтобы мутацию можно было проверить, каждая проверка тестов 2–7 — функция модуля теста, которая принимает разобранный JSON и текст MD; метод `unittest` вызывает её на закоммиченных файлах. Мутационный прогон — отдельный разовый скрипт в `.tmp/`, который вызывает эти функции на изменённых копиях; в репозиторий он не входит. Строки его вывода — каждая мутация краснеет — показать в сдаче.

Команда проверки (полная, других наборов не добавлять):

```
PYTHONDONTWRITEBYTECODE=1 D2TM_PACK_DIR=/srv/dune/inputs/packs /srv/dune/venv/bin/python -m unittest discover -s tools/units3d/tests -v
```

Перед написанием кода каждый новый или изменённый тест должен упасть — красный прогон показать в сдаче.

## Не трогать

`src/`, `tests/`, `resources/`, `CMakeLists.txt`, существующие файлы `tools/`. Паки не изменять.

## Чего задача не делает

Не рисует и не рендерит юниты; не выбирает угол камеры; не решает, какие юниты получат новые модели.

## Организация работы

- Порядок: разбор `UNITS` для `sega_reference` → красные тесты 2, 4–7 и мутационный скрипт → правки скрипта по `answer-02.md` → пересборка JSON и MD → зелёный прогон и мутации → один круг самоаудита → `DONE-a1`.
- Параллельно: пункты `answer-02.md` не зависят друг от друга, кроме общей пересборки JSON и MD в конце; запускай их сразу, одновременно.
- Помощники: субагенты `gpt-6-luna` `xhigh`; независимые части запускай сразу, по одному на пункт `answer-02.md`, одновременно до 8 — красные тесты, мутационный скрипт, поиск ссылок на строки-комментарии, прогон тестов, выжимки логов.
- Остановки: известный случай теста расходится с источником, запись без Sega-листа или место отрисовки, которое скрипт не разобрал, — `Q` и стоп; сдача — `DONE-a1` после зелёного прогона и красных мутаций.
- Рамка правок: только `tools/units3d/unit_contract.py`, `tools/units3d/tests/test_unit_contract.py`, `docs/units/unit_contract.json`, `docs/units/UNIT_CONTRACT.md`; рабочие файлы и логи — в `.tmp/`; правка вне рамки — `Q` до правки.
