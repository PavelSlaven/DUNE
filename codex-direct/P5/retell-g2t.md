### Что и в каком порядке я делал бы в P5G2T

По моему прочтению, P5G2T требует подготовить **тесты будущей реализации**, а не реализовать сцены и не добиться зелёных прогонов сейчас.

Предписанный порядок такой:

1. Зарегистрировать цель дословным текстом раздела «Цель». Прочитать полностью, отдельными вызовами, три файла: `ui_audit_runtime_support.py`, `ui_audit_main_menu_png.py`, `check_credits.py`.
2. Проверить отсутствие обоих новых файлов. Если хотя бы один существует, остановиться с `## Q-P5G2T-05`.
3. Создать два файла Python, дословно повторив приведённый код. Корневая нить выполняет создание и сверку.
4. Передать одному помощнику `gpt-6-luna` с усилием `xhigh` шаг 2, дословный абзац о комментариях и ограничения на изменения. Помощник компилирует скрипты, выполняет H и I, собирает требуемые строки логов и удаляет возникший `tests/ui_audit/__pycache__`.
5. Если выявлено собственное отклонение от приведённого текста, корневая нить исправляет копирование, а помощник повторяет шаг 2 с компиляции. Если файлы совпадают с заданием, но результаты отличаются от ожидаемых, требуется остановка, а не подгонка тестов.
6. После ожидаемых красных прогонов корневая нить записывает SHA-256 четырёх файлов и больше их не меняет.
7. Проверить, что Git показывает ровно два новых файла тестов. Подготовить сдачу с логами, хэшами, списком будущего коммита и инвентаризацией папки задачи.

Сборка, реализация сцен и коммиты в задачу не входят. Ведущий затем коммитит два новых файла по списку из сдачи. Будущий исполнитель части 2 реализует поведение по контракту, сохраняя тесты неизменными.

### Прогоны H и I

Это **ожидания задания**, а не полученные мной результаты.

**Перед H и I:** `py_compile` должен закончиться с `exit=0`.

**H:** каталог установленной игры содержит только `main-menu`, поэтому ожидается `exit=1`.

Первая строка лога должна начинаться с:

```text
Part 2 scenes differ: missing [
```

Она должна содержать `'choose-house'` и `; extra []`. Это следует из вычисления `missing` и `extra` и возврата:

```python
return f"Part 2 scenes differ: missing {missing}; extra {extra}"
```

В логе не должно быть `must not write preferences`. Однако при ошибке каталога `main()` возвращает `1` **до вызова** `preferences_files()`. Поэтому отсутствие такой строки в H само по себе не доказывает отсутствия записанного файла настроек.

**I:** все 24 запуска относятся к неизвестным установленной игре сценам. Ожидается `exit=1`, а не завершение внешнего `timeout`.

Требуются:

- 24 строки, содержащие `game exited with 2`;
- 24 строки, содержащие `ui-audit: unknown scene`;
- последняя строка `credits coverage: combos 0, problems []`;
- отсутствие `must not write preferences`.

Сообщение `game exited with 2` формирует `run_scene()` при ненулевом коде игры; стандартные потоки игры включаются в ошибку. Цикл собирает ошибки по всем сценам, затем добавляет результат проверки титров. Поведение установленной игры и результат `(0, [])` при отсутствии титров заявлены заданием; реализация общего проверяющего модуля не приведена.

### Атаки

Ниже описаны варианты кода будущей части 2. Это разбор проверок по тексту, без экспериментальных прогонов; тесты и общие помощники в примерах не изменяются.

**Красный R1 — картинка не соответствует экрану.**  
Код формирует правильный каталог и корректные журналы, включая настоящее полное покрытие титров, но вместо изображения каждого экрана сохраняет одинаковый корректный одноцветный PNG размером `1024 × 768`. `ui_audit_part2_catalog.py` проверяет только каталог, а `ui_audit_part2_scenes.py` явно проверяет размер и структуру вывода, без сопоставления пикселей с экраном: при выполнении заявленной роли `png_size` оба теста проходят, хотя цель получить сцены экранов форка нарушена.

**Красный R2 — записи выдуманы отдельно от раскладки порта.**  
Код действительно показывает нужные экраны, но журнал собирает отдельная таблица констант: например, у `house-back` пишет положительный прямоугольник далеко за холстом вместо прямоугольника реальной кнопки, сохраняя остальные проверяемые сведения правильными. Каталог проходит, а `check_choose_house()` в `ui_audit_part2_scenes.py` проверяет для этой записи только единственность и положительные `w/h`; связь записи с раскладкой порта не проверяется, поэтому нарушается цель шага.

**Красный R3 — 83 сцены существуют только в каталоге.**  
Код объявляет все 107 записей, корректно реализует 24 сцены из `SCENES`, а для остальных 83 возвращает «unknown scene». `ui_audit_part2_catalog.py` принимает правильные метаданные, `ui_audit_part2_scenes.py` остальные сцены не запускает: оба проходят, хотя заявленное добавление 107 сцен не выполнено; пункты 6–8 отдельно распространяют требования запуска именно на выбранные 24.

**Красный R4 — невалидный JSON и неположительная в смысле контракта площадь.**  
В остальном правильный журнал `choose-house` код записывает с некавыченным `NaN` в поле `w` одной обязательной кнопки. Стандартный `json.loads` Python принимает `NaN`, проверка ключей проходит, а в `sized_click()` условие `w <= 0` ложно: скрипт сцен пропускает запись, каталог не затрагивается, но нарушены стандартный JSON пункта 6 и требование `w > 0` пункта 7.

Для R4 я выбираю стандартное значение слова JSON. Если автор намеренно включает расширения парсера Python, нарушение синтаксиса перестаёт быть аргументом, но `NaN > 0` всё равно не выполняется.

**Зелёный G1 — допустимый символ внутри строкового `version`.**  
Полностью соответствующий контракту код сериализует заголовок в UTF-8 с буквальным символом U+2028 внутри `version`, например между `v1` и `build`, оставляя разделителями записей LF. Такая строка допустима в JSON, `version` остаётся строкой, но `ui_audit_part2_scenes.py` вызывает `splitlines()`, разрезает JSON внутри строкового значения и затем отвергает его через `json.loads`; каталог остаётся зелёным.

Этот случай выполняет контракт при обычном прочтении JSONL с разделителем LF. При альтернативном прочтении «строки» через все Unicode-разделители текста он становится спором о формулировке, а не безусловным зелёным примером.

**Зелёный G2 — обратное направление строк, условный случай.**  
Код выдаёт правильные размеры и столбцы схватки, но значения `y` строк идут как `300, 274, 248, 222`: соседние значения отличаются ровно на 26. При буквальном прочтении разницы как модуля пункт 7 выполнен, однако `check_skirmish_rows()` в `ui_audit_part2_scenes.py` получает шаги `{-26}` и отвергает их вместо ожидаемых `{26}`; при прочтении «следующая строка ниже» этот пример контракту не соответствует.

Я не заявляю отдельные атаки на проверку `IDAT`/`IEND`, поиск настроек или внутреннее покрытие титров: без исходников общих помощников их пропуск или ложное отклонение по предоставленному тексту установить нельзя.
