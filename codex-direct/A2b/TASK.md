# Задание A2b — приёмочные проверки конвейера юнитов

Режим: **«План у ревьюера»** (см. «Режимы задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/a2b`. Спецификация — `docs/units/UNITS3D_SPEC.md` (дальше «спека»); контракт — `docs/units/unit_contract.json` (результат задания A1).

## Цель

Написать до реализации конвейера проверяющий скрипт `tools/units3d/check_unit.py` (проверки 1–10 раздела 5 спеки) и тесты, которые доказывают, что каждая проверка ловит своё нарушение и пропускает честный случай, плюс приёмочный тест конвейера на учебной модели, который сейчас красный, потому что команд 1–3 спеки ещё нет.

## Что сделать

1. `tools/units3d/check_unit.py` — интерфейс и вывод строго по разделу 3, команда 4 спеки; проверки и пороги — по таблице раздела 5, номера 1–10. Проверка 2 сравнивает пак до и после установки: путь к паку «до» — аргумент `--pack-before`, «после» — `--pack-after`; без этих аргументов проверка 2 печатает `SKIP` и не влияет на код выхода только если `--allow-skip 2` передан явно.
2. `tools/units3d/tests/test_check_unit.py` (`unittest`): для каждой проверки 1–10 — минимум один честный случай (`PASS`) и минимум один случай нарушения (`FAIL` именно этой проверки, остальные `PASS`). Случаи строятся в тесте из numpy/Pillow во временной папке `.tmp/`; файлы-образцы в репозиторий не класть. Пограничные значения порогов (ровно на пороге и на 1 единицу за ним) — для проверок 3, 4, 5, 6, 9.
3. Учебная модель: `tools/units3d/tests/fixtures/make_box_tank.py` — скрипт Blender, который строит модель «коробка-корпус + цилиндр-башня + ствол» одной сеткой, с текстурой из двух цветов, и сохраняет `tools/units3d/tests/fixtures/box_tank/source/box_tank.glb`; там же `unit.json` по образцу раздела 2 спеки с записями `UNIT_TANKBASE`, `UNIT_TANKBASE_SHADOW`, `HM_UNIT_TANKBASE`, `UNIT_TANKTOP`, `HM_UNIT_TANKTOP` и разрезкой башни. GLB коммитится (размер до 200 КБ).
4. `tools/units3d/tests/test_pipeline_acceptance.py`: прогоняет команды 1, 2, 3 спеки на учебной модели в `.tmp/` и затем `check_unit.py` со всеми проверками 1–10 (`--pack-before` — `/srv/dune/inputs/packs/sdl_data_hd4.dat`, `--pack-after` — копия после установки); тест проходит только при коде выхода 0. Отдельный тест проверки 11 — два прогона команд 1–2 и сравнение по порогу спеки. Путь к Blender — переменная `D2TM_BLENDER`, к пакам — `D2TM_PACK_DIR`; без них тесты пропускаются с сообщением.
5. Файл `tools/units3d/tests/ACCEPTANCE.sha256` — SHA-256 файлов из пунктов 1–4. После приёмки ведущим эти файлы меняет только старшая модель по вопросу `Q` исполнителя реализации.

## Доказательства в сдаче

- Прогон `test_check_unit.py`: все тесты зелёные; для каждого случая нарушения в выводе видно, какая проверка дала `FAIL`.
- Прогон `test_pipeline_acceptance.py`: красный по заявленной причине — нет `tools/units3d/render_unit.py` (строка ошибки в сдаче). Красный по любой другой причине — исправить тест.
- Каждая проверка 1–10 в `check_unit.py` — строка таблицы «номер → функция → честный тест → тест нарушения».

Команда проверки (полная):

```
D2TM_PACK_DIR=/srv/dune/inputs/packs D2TM_BLENDER=/srv/dune/tools/blender-5.2.3-linux-x64/blender /srv/dune/venv/bin/python -m unittest discover -s tools/units3d/tests -v
```

## Если спека неоднозначна

Каждое место спеки, которое допускает два прочтения с разным результатом проверки, — вопрос `Q` до работы с обоими прочтениями и рекомендацией. Порог не выбирать самому.

## Не трогать

`src/`, `tests/`, `resources/`, `docs/`, тесты и файлы задания A1. Команды 1–3 спеки не писать — это задание A2a.

## Чего задача не делает

Не рендерит модели пилота; не выбирает угол, масштаб и зоны Дома; не проверяет снимки в игре.
