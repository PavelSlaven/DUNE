# Задание A2b2 — поле `cap_height_m` у юнита без башни

Режим: **«План у ревьюера»** (см. «Режим задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/a2b2` от `main` (`f9bed798`). Рабочая копия: `/srv/dune/worktrees/a2b2`.

## Цель

`tools/units3d/check_unit.py` требует, чтобы `cap_height_m` в `render_manifest.json` было числом у любого юнита. Это строка 229, функция `_manifest_schema`, цикл по полям с вызовом `_number`. У юнита без детали `top` крышки нет. Это, например, Девастатор: в `parts` его `unit.json` есть только `body`. Конвейер рендера пишет ему `"cap_height_m": null`, и проверки 1, 3, 6 и 10 честного рендера дают `FAIL` с причиной `render_manifest.json.cap_height_m: ожидается число`.

Ведущий решил это пробелом спецификации и записал новое правило в спецификацию конвейера. Правило дословно, раздел 4 `docs/units/UNITS3D_SPEC.md` (в ветке `main` этого файла нет, текст правила — здесь):

> `cap_height_m` (высота крышки `cap_z` над нижней точкой модели в метрах после масштабирования; ключ есть всегда: у юнита, у которого в `parts` файла `unit.json` есть `top`, значение — конечное число, у юнита без `top` — `null`; другое значение или нет ключа — ошибка чтения входа `render_manifest.json`, раздел 3)

«Конечное число» здесь — значение, которое принимает нынешняя функция `_number` (`check_unit.py:92–96`): `int` или `float`, не `bool`, конечное. `null` — JSON `null`, в Python — `None`.

Ошибка чтения входа `render_manifest.json` по разделу 3 спецификации даёт:
- `FAIL` с причиной у каждой проверки, которая читает этот вход: 1, 3, 6 и 10;
- строки всех 10 проверок в выводе, без исключения;
- код выхода ≠ 0.

Остальные проверки (2, 4, 5, 7, 8, 9) дают тот же статус, что на честном наборе. Скрипт уже так обрабатывает ошибку чтения `render_manifest.json`; это поведение не меняется.

`check_unit.py` и `tests/test_check_unit.py` заморожены хэшем в `tools/units3d/tests/ACCEPTANCE.sha256`. Это задание — разрешённая правка старшей моделью по вопросу исполнителя конвейера.

## Что сделать

1. **`tools/units3d/check_unit.py`.** Проверка `cap_height_m` в `_manifest_schema` — строго по правилу выше:
   - деталь `top` есть в `parts` из `unit.json` → значение проверяет `_number`;
   - детали `top` нет → значение `None`;
   - ключа нет → ошибка чтения входа при любом составе `parts`.

   Другие поля, проверки и сообщения не меняются. Правка, которая затрагивает в `check_unit.py` что-то кроме проверки `cap_height_m`, — вопрос `Q` до правки.
2. **`tools/units3d/tests/test_check_unit.py`.**
   - **Синтетический манифест.** Строитель синтетического `render_manifest.json` (сейчас строка 309, `"cap_height_m": 0` для любого юнита) пишет у юнита без `top` значение `None`, у юнита с `top` — прежнее `0`.
   - **Честные случаи.** Существующий честный прогон юнита без `top` (`_check4_cli("blue_zero_without_top", set(), with_top=False)`, строка 1281) остаётся зелёным с `None`. Добавь честный полный прогон юнита без `top` с `cap_height_m = None`: все 10 проверок `PASS`, код выхода 0, пак передан. Если такой прогон уже есть — назови его в DONE.
   - **Красные случаи.** Каждый красный случай меняет в честном наборе только значение или наличие ключа `cap_height_m`. Тест проверяет через `assert_run` точный набор `FAIL` = {1, 3, 6, 10}, остальные проверки — `PASS`, код выхода ≠ 0, и что причина `FAIL` у проверки 1 содержит `cap_height_m`. Случаи:

     | № | Юнит | `cap_height_m` в манифесте |
     |---|---|---|
     | К1 | с `top` | `null` |
     | К2 | с `top` | ключа нет |
     | К3 | с `top` | строка `"0.5"` |
     | К4 | с `top` | `true` |
     | К5 | с `top` | `Infinity` (JSON-токен, который пишет `json.dumps(float("inf"))`) |
     | К6 | без `top` | `0` |
     | К7 | без `top` | `0.5` |
     | К8 | без `top` | ключа нет |
     | К9 | без `top` | строка `"null"` |
     | К10 | без `top` | `false` |

   - Если точный набор `FAIL` у случая выходит не {1, 3, 6, 10} — `Q` с выводом прогона. Тест не ослабляй, набор не подгоняй.
3. **`tools/units3d/tests/ACCEPTANCE.sha256`.** Пересчитать обе строки в формате вывода `sha256sum` (`<hex>  <путь от корня репозитория>`); проверка — `sha256sum -c tools/units3d/tests/ACCEPTANCE.sha256`.

## Доказательство красным

Каждый новый красный случай должен краснеть хотя бы на одной мутации ниже. На настоящем `check_unit.py` все случаи зелёные. Мутации делаются только в копиях рабочей копии внутри `.tmp/mut/<имя>/` с той же раскладкой `tools/units3d/` и `tools/hd_assets.py`; сам `tools/units3d/check_unit.py` не трогать. В копии запускай только затронутые тесты.

| Имя | Что меняется в копии `check_unit.py` после твоей правки | Какие случаи должны покраснеть |
|---|---|---|
| MC1 | значение `None` принимается при любом составе `parts` | К1 |
| MC2 | у юнита без `top` принимается любое значение и отсутствие ключа | К6, К7, К8, К9, К10 |
| MC3 | отсутствие ключа считается значением `None` | К8 |
| MC4 | прежнее правило: `_number` при любом составе `parts` | честные прогоны юнита без `top` (строка 1281 и новый полный прогон) |
| MC5 | у юнита с `top` принимается любое значение и отсутствие ключа | К1, К2, К3, К4, К5 |

В DONE по каждой мутации — путь к логу, строки итога и список покрасневших тестов: красный на мутации, зелёный на настоящем коде. Случай из правого столбца, который на своей мутации остался зелёным, — `Q` с логом.

## Организация работы

- Порядок: PLAN → тесты К1–К10, честные прогоны без `top` и правка строителя манифеста, прогон этих тестов на нынешнем `check_unit.py` (до правки красными должны быть только К6, К7 и честные прогоны юнита без `top`; остальные случаи нынешнее правило уже отвергает; список красных до правки — в DONE со ссылкой на лог) → правка `check_unit.py` → зелёный прогон затронутых тестов → мутации MC1–MC5 → полный прогон с паками → `ACCEPTANCE.sha256` → `DONE-A2b2`.
- Параллельно: мутационные прогоны MC1–MC5 независимы — запускай их сразу, одновременно, каждый в своей копии.
- Помощники: `gpt-6-luna` `xhigh`, независимые части — сразу, до 5 одновременно: мутационные копии и прогоны, выжимки логов. Построение случаев и итоговая сверка — твои.
- Остановки: `Q` и стоп, если точный набор у случая не {1, 3, 6, 10}, если правка `check_unit.py` затрагивает что-то кроме проверки `cap_height_m` или если честный прогон без `top` краснеет по другой причине; сдача — `DONE-A2b2` после зелёного полного прогона.
- Рамка правок: только `tools/units3d/check_unit.py`, `tools/units3d/tests/test_check_unit.py`, `tools/units3d/tests/ACCEPTANCE.sha256` и `.tmp/`; правка вне рамки — `Q` до правки.
