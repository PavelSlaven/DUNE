# Задание A2b2 — поле `cap_height_m` у юнита без башни

Режим: **«План у ревьюера»** (см. «Режим задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/a2b2` от `main` (`f9bed798`). Рабочая копия: `/srv/dune/worktrees/a2b2`.

## Цель

`tools/units3d/check_unit.py` требует, чтобы `cap_height_m` в `render_manifest.json` было числом у любого юнита. Это строка 229, функция `_manifest_schema`, цикл по полям с вызовом `_number`. У юнита без детали `top` крышки нет. Это, например, Девастатор: в `parts` его `unit.json` есть только `body`. Конвейер рендера пишет ему `"cap_height_m": null`, и проверки 1, 3, 6 и 10 честного рендера дают `FAIL` с причиной `render_manifest.json.cap_height_m: ожидается число`.

Ведущий решил это пробелом спецификации и записал новое правило в спецификацию конвейера. Правило дословно, раздел 4 `docs/units/UNITS3D_SPEC.md` (в ветке `main` этого файла нет, текст правила — здесь):

> `cap_height_m` (высота крышки `cap_z` над нижней точкой модели в метрах после масштабирования; ключ есть всегда: у юнита, у которого в `parts` файла `unit.json` есть `top`, значение — конечное число, у юнита без `top` — `null`; другое значение или нет ключа — ошибка чтения входа `render_manifest.json`, раздел 3)

Как читать правило:
- **«Конечное число»** — значение, которое принимает нынешняя функция `_number` (`check_unit.py:92–96`): `int` или `float`, не `bool`, конечное. Знак, диапазон и точность не ограничиваются.
- **`null`** — JSON `null`, в Python — `None`.
- **Есть ли `top`** — по ключам отображения `parts` из `unit.json`, то есть `unit["parts"]`, который получает `_manifest_schema`. Список `parts` из `render_manifest.json` для этого правила не используется.

Ошибка чтения входа `render_manifest.json` по разделу 3 спецификации даёт:
- `FAIL` с причиной у каждой проверки, которая читает этот вход: 1, 3, 6 и 10;
- строки всех 10 проверок в выводе;
- код выхода ≠ 0.

Остальные проверки (2, 4, 5, 7, 8, 9) дают тот же статус, что на честном наборе. Скрипт уже так обрабатывает ошибку чтения `render_manifest.json`; это поведение не меняется.

`check_unit.py` и `tests/test_check_unit.py` заморожены хэшем в `tools/units3d/tests/ACCEPTANCE.sha256`. Это задание — разрешённая правка старшей моделью по вопросу исполнителя конвейера.

## Что сделать

### 1. `tools/units3d/check_unit.py`

Проверка `cap_height_m` в `_manifest_schema`:
- **Ключа `cap_height_m` нет** — ошибка с текстом `render_manifest.json.cap_height_m: нет ключа`, при любом составе `parts`.
- **Ключ `top` есть в `unit["parts"]`** — значение проверяет `_number` с его нынешними текстами ошибок.
- **Ключа `top` в `unit["parts"]` нет** — значение должно быть `None`. Иначе ошибка с текстом `render_manifest.json.cap_height_m: у юнита без top ожидается null`.

Проверка остаётся на месте нынешнего вызова в цикле `_manifest_schema`, чтобы порядок первых ошибок при нескольких плохих полях не изменился. Другие поля, проверки и сообщения не меняются. Правка, которая затрагивает в `check_unit.py` что-то кроме проверки `cap_height_m`, — вопрос `Q` до правки.

### 2. `tools/units3d/tests/test_check_unit.py`

Новые тесты — в новом классе рядом с `InputReadFailureTests`.

**а) Синтетический манифест.** Строитель синтетического `render_manifest.json` пишет `cap_height_m`:
- у юнита без `top` — `None`;
- у юнита с `top` — прежнее `0`.

Сейчас он пишет `"cap_height_m": 0` для любого юнита (строка 309).

**б) Честные полные прогоны.** С `None` у юнита без `top` зелёными остаются:
- `CompositionCheckTests.test_honest_body_only_and_body_with_top` (строка 754): его ветвь без `top` через `Fixture.__enter__` проверяет все 10 `PASS`, код выхода 0 и передаёт паки;
- `test_body_only_zero_blue_channels_are_allowed` (строка 1280).

Нового полного честного теста не нужно.

**в) Сквозные красные случаи** (запуск скрипта через `assert_run`).

Каждый случай меняет в честном наборе одно: значение `cap_height_m` или наличие ключа. Зависимые хэши `render_manifest.json`, которые `Fixture.commit()` пересчитывает в `atlases.json` при `update_hashes=True`, пересчитываются этим вызовом: это не второе изменение. Остальные данные набора не меняются.

Тест проверяет:
- точный набор `FAIL` = {1, 3, 6, 10}, остальные проверки — `PASS`;
- код выхода ≠ 0;
- причина `FAIL` у каждой из проверок 1, 3, 6 и 10 содержит `cap_height_m`.

| № | Юнит | `cap_height_m` в манифесте |
|---|---|---|
| К1 | с `top` | `null` |
| К2 | с `top` | ключа нет |
| К3 | с `top` | строка `"0.5"` |
| К4 | с `top` | `true` |
| К5 | с `top` | список `[0.5]` |
| К6 | без `top` | `0` |
| К7 | без `top` | `0.5` |
| К8 | без `top` | ключа нет |
| К9 | без `top` | строка `"null"` |
| К10 | без `top` | `false` |

**г) Прямая проверка схемы.** Табличный тест вызывает `_manifest_schema(manifest, unit)` из `check_unit.py` напрямую. Каждое значение — отдельный `subTest`, остальной манифест — честный. «Принимается» — вызов без исключения. «Отвергается» — `CheckError`, текст которого содержит `cap_height_m`.

| Набор | `unit["parts"]` | `manifest["parts"]` | Принимается | Отвергается |
|---|---|---|---|---|
| Г1 | с `top` | с `top` | `0`, `0.0`, `-0.0`, `0.5`, `-1`, `1e-3`, `1e308` | `None`, нет ключа, `"0.5"`, `"0"`, `""`, `True`, `False`, `[]`, `{}`, `[0]`, `{"value": 0}` |
| Г2 | без `top` | без `top` | `None` | нет ключа, `0`, `0.0`, `-0.0`, `0.5`, `-1`, `True`, `False`, `"null"`, `""`, `[]`, `{}` |
| Г3 | с `top` | без `top` (`["body"]`) | `0.5` | `None` |
| Г4 | без `top` | с `top` (`["body", "top"]`) | `None` | `0.5` |

Если `_manifest_schema` отвергает наборы Г3 или Г4 по другой причине, чем `cap_height_m`, — `Q` с выводом.

**д) Вне задания.** Сюда не входят:
- значения, которые разбор JSON отвергает до проверки схемы: токены `Infinity` и `NaN` (`parse_constant`), число `1e309` (`_finite_tree`);
- целые, которые не помещаются во `float`: `_number` падает на них с `OverflowError`. Это общий дефект всех числовых полей; ведущий вынесет его отдельной задачей.

Эти случаи не пиши и это поведение не меняй.

### 3. `tools/units3d/tests/ACCEPTANCE.sha256`
