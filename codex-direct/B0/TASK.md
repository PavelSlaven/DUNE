# Задание B0 — карта переноса функций форка на свежий апстрим

Режим: **«Ведёт sol»** (см. «Режимы задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/b0`. План работ проекта: `docs/PLAN_units_sega_upstream.md`, раздел 3.2 и шаг Б0.

## Цель

Создать:
- детерминированный скрипт `tools/upstream/port_inventory.py`, который строит `docs/upstream/port_inventory.json` для трёх точек истории;
- файл правил `tools/upstream/port_features.json`: список функций форка и правила, какие пути к какой функции относятся;
- документ `docs/upstream/PORT_MAP.md`, который для каждой функции форка говорит, какие файлы её несут, что с этими файлами сделал апстрим, какие тесты форка её проверяют и как её переносить;
- тест `tools/upstream/tests/test_port_inventory.py`.

## Точки истории

- `BASE` = `e17379ad` — общий предок форка и апстрима (проверить командой `git merge-base`; другое значение — `Q`).
- `FORK` = `6662b2f4857c679425ea2166092a21f4bde7d6e7` — `origin/main` форка.
- `UP0` = `a51b97f15d0eee2d323a1737f140eb2cbd60973c` — `upstream/master`, закреплённый на время переноса.

Все три коммита и вся история между ними уже есть в рабочей копии (remotes `origin` и `upstream`). Сети нет. В рабочей копии файлы Git LFS лежат указателями; содержимое паков форка — в `/srv/dune/inputs/packs/` (только чтение).

## 1. Скрипт и `port_inventory.json`

Вызов: `python tools/upstream/port_inventory.py --packs <папка паков> --out <путь JSON>`.

Скрипт читает историю только командами `git diff --name-status -M -z`, `git diff --numstat`, `git log`, `git show <коммит>:<путь>`, `git cat-file --batch`, `git ls-tree`, `git check-attr`, `git merge-base`, `git rev-list`. Содержимое файла в коммите берётся только через `git show` или `git cat-file --batch`; восстанавливать файлы наложением патчей из `git log -p` запрещено. Паки читаются функцией `read_pack` из `tools/hd_assets.py`. JSON пишется с ключами в отсортированном порядке.

### 1.1. Пути — раздел `paths`

Для каждого пути, изменённого хотя бы с одной стороны:
- `fork`: статус `BASE..FORK` (`A`, `M`, `D` или `R` с исходным путём), число добавленных и удалённых строк, признак двоичного файла; `null`, если форк путь не менял;
- `upstream`: то же для `BASE..UP0`;
- `overlap`: `true`, если путь изменён с обеих сторон, включая случай, когда апстрим переместил или удалил файл, который форк менял;
- `lfs`: `true`, если путь в форке подпадает под правило `filter=lfs` из `.gitattributes`;
- `features`: только у путей с `fork` не `null` — отсортированный список `id` функций, к которым путь отнесён правилами из `tools/upstream/port_features.json` (раздел 1.2). Один путь может относиться к нескольким функциям.

### 1.2. Функции — файл правил и раздел `features`

`tools/upstream/port_features.json` пишет sol. Формат:

```
{
  "features": [
    {"id": "<латиница, строчные, через дефис>", "title": "<название по-русски>",
     "source": "README_AI §1" | "fork_commits",
     "port_class": "copy" | "reapply" | "rewrite",
     "depends_on": ["<id>", ...], "steps": ["Б3", ...],
     "include": ["<шаблон пути>", ...]}
  ]
}
```

- Список функций — из `README_AI.md` §1 в `FORK`, сверенный с заголовками `fork_commits`; функция, найденная в коммитах, но не в §1, получает `"source": "fork_commits"`.
- `port_class`: `copy` — «копировать как есть» (файлы, которых апстрим не трогал и которые не зависят от изменённых апстримом); `reapply` — «применить заново» (апстрим менял те же файлы, архитектура та же); `rewrite` — «переписать под новую архитектуру» (код форка опирается на удалённое или перемещённое апстримом).
- `steps` — шаги Б3–Б12 плана, в которых функция переносится; порядок функций в списке — рекомендованный порядок переноса.
- `include` — шаблоны `fnmatch.fnmatchcase` (знак `*` совпадает и с `/`), применяются к путям `FORK`. Путь относится к функции, если совпал хотя бы с одним её шаблоном. Точный путь — тоже шаблон.

Скрипт копирует `features` из файла правил в JSON (без поля `include`) и добавляет каждой функции `paths_count` — число путей, отнесённых к ней.

### 1.3. Коллизии — раздел `id_collisions`

Список записей, у каждой поле `kind`:
- `define_pair`: пары `#define` с одинаковым числовым значением в файлах `src/data/*.h`, где одно имя добавил форк, другое — апстрим. Поля: `header`, `value`, `fork_name`, `upstream_name`.
- `pack_index_taken` и `pack_index_missing`: для пар «заголовок — HD4-пак форка» `src/data/gfxdata.h` — `sdl_data_hd4.dat`, `src/data/gfxinter.h` — `sdl_inter_hd4.dat`, `src/data/gfxmentat.h` — `sdl_mentat_hd4.dat`, `src/data/gfxworld.h` — `sdl_world_hd4.dat`. Для каждого `#define <ИМЯ> <целое>` из заголовка в `UP0`, имени которого нет в том же заголовке в `BASE`: если в HD4-паке форка есть запись с индексом, равным значению, и её имя не равно `<ИМЯ>` — запись `pack_index_taken`; если записи с таким индексом нет — `pack_index_missing`. Поля: `header`, `pack`, `define`, `value`, `fork_entry` (имя записи пака или `null`). Правило не отличает индекс записи от другой числовой константы: запись, чей `#define` по коду `UP0` не индекс записи пака (например, число элементов), всё равно остаётся в JSON, а в `PORT_MAP.md` помечается «не индекс» со ссылкой `путь@UP0:строка`.

Паки берутся из папки `--packs`. Перед чтением скрипт сверяет sha256 каждого пака с oid указателя LFS этого пути в `FORK` (`git show FORK:resources/bin/data/<пак>`); расхождение — выход с ошибкой. Раздел `packs` JSON: `{<имя пака>: <sha256>}`.

### 1.4. SDL2 в коде форка — раздел `sdl2_in_fork_code`

Идентификатор — токен по регулярному выражению `\b(?:SDL|Mix|MIX|IMG|TTF)_\w+`, а также путь подключения вида `SDL2/<файл>` из строк `#include`. Множество подтверждённых — все такие токены, которые встречаются хотя бы в одном файле дерева `src/` в `UP0`. Для каждого файла `src/`, который форк добавил, изменил или переместил: `identifiers` — отсортированный список токенов файла в `FORK`, которых нет среди подтверждённых; `lines` — число строк файла в `FORK`, где есть хотя бы один такой токен. В JSON попадают только файлы с `lines > 0`; отдельное поле `sdl2_lines_total` — сумма. Шаблоны «что апстрим поменял в `BASE..UP0`» больше не используются.

### 1.5. Коммиты — раздел `fork_commits`

Коммиты `BASE..FORK` (sha, дата, заголовок, изменённые пути).

## 2. `docs/upstream/PORT_MAP.md`

Документ пишет sol по JSON. Размер — не больше 80 000 байт. Построчного приложения «путь → функция» в документе нет: отнесение путей хранится только в JSON.

1. **Функции форка** — таблица в порядке `features`: `id`, название, источник, класс переноса, зависимости, шаги, `paths_count`. Под таблицей для каждой функции:
   - все её пути под `src/`, `tests/` и `CMakeLists.txt` — списком, у каждого судьба в апстриме: не менялся / изменён / перемещён в `<путь>` / удалён — и куда в `UP0` ушёл код, если удалён (класс или файл);
   - остальные её пути — числом по каталогу второго уровня (например, `resources/hd: 1723`);
   - тесты форка из `tests/*.cpp`, которые её проверяют (по именам тестов и по тому, какие файлы они включают, с учётом транзитивных `#include`).
2. **Данные и паки:** какие двоичные паки менялись с обеих сторон (особенно `resources/bin/data/sdl_inter.dat`); все записи `id_collisions` из JSON таблицей. Подтверждённая коллизия индекса 167 (`HM_BUILD_REFINERY` в `sdl_data_hd4.dat` против `EXPLOSION_CARRYALL` в `src/data/gfxdata.h` апстрима) называется фактом со ссылкой на issue PavelSlaven/DUNE#2 и шаг Б2 плана.
3. **Аддитивное:** что из форка переносится копированием (папки `resources/hd`, `tools`, `packaging`, `README_AI.md`, тесты форка и другие, найденные по JSON) — числами по каталогам.
4. **SDL2:** правило подсчёта из раздела 1.4 своими словами, сумма и файлы с наибольшим `lines`; одной фразой — чего подсчёт не видит (функции, у которых в SDL3 то же имя, но другая сигнатура).
5. **Риски переноса,** которые видны по JSON, — каждый с путём файла.
6. **Сверка чисел плана:** каждое число из шага Б0 и раздела 3.2 плана, которое не совпадает с JSON, — одной строкой: из каких статусов JSON оно складывается.

Каждое утверждение о коде — со ссылкой `путь@коммит:строка`, где строка содержит названный символ, или путём файла из JSON. Не уверен — пометка «не проверено».

## Тест

`tools/upstream/tests/test_port_inventory.py` на `unittest`. Путь к пакам — переменная окружения `D2TM_PACK_DIR`; без неё тесты, которым нужны паки, пропускаются с сообщением.
1. Скрипт, запущенный во временную папку, выдаёт JSON, побайтно равный закоммиченному.
2. Каждый путь со статусом `overlap: true` в JSON действительно изменён в обоих диапазонах (`git diff --quiet` по пути даёт код 1 для каждого диапазона, или путь перемещён или удалён).
3. Каждый путь файла, упомянутый в `PORT_MAP.md` в обратных кавычках, есть в `FORK` или в `UP0`.
4. Охват: у каждого пути с `fork` не `null` непустой `features`; каждый шаблон `include` совпадает хотя бы с одним путём `FORK`, изменённым форком; каждый `id` из `depends_on` есть в `features`; у каждой функции `paths_count > 0`.
5. Размер `PORT_MAP.md` не больше 80 000 байт.

Команда проверки (полная):

```
D2TM_PACK_DIR=/srv/dune/inputs/packs /srv/dune/venv/bin/python -m unittest discover -s tools/upstream/tests -v
```

## Не трогать

`src/`, `tests/`, `resources/`, `CMakeLists.txt`, существующие файлы `tools/`. Не делать merge, cherry-pick и не переносить код — это следующие шаги.

## Чего задача не делает

Не собирает игру и не запускает тесты C++ (это шаг Б1); не решает за владельца ничего, кроме порядка переноса, который потом утверждает ведущий.
