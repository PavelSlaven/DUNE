# Задание B0 — карта переноса функций форка на свежий апстрим

Режим: **«Ведёт sol»** (см. «Режимы задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; механика — субагентам `gpt-6-luna` `xhigh`.
Ветка: `codex/b0`. План работ проекта: `docs/PLAN_units_sega_upstream.md`, раздел 3.2 и шаг Б0.

## Цель

Создать детерминированный скрипт `tools/upstream/port_inventory.py`, который строит `docs/upstream/port_inventory.json` для трёх точек истории, и документ `docs/upstream/PORT_MAP.md`, который для каждой функции форка говорит, какие файлы её несут, что с этими файлами сделал апстрим, какие тесты форка её проверяют и как её переносить; плюс тест `tools/upstream/tests/test_port_inventory.py`.

## Точки истории

- `BASE` = `e17379ad` — общий предок форка и апстрима (проверить командой `git merge-base`; другое значение — `Q`).
- `FORK` = `6662b2f4857c679425ea2166092a21f4bde7d6e7` — `origin/main` форка.
- `UP0` = `a51b97f15d0eee2d323a1737f140eb2cbd60973c` — `upstream/master`, закреплённый на время переноса.

Все три коммита и вся история между ними уже есть в рабочей копии (remotes `origin` и `upstream`). Сети нет.

## 1. Скрипт и `port_inventory.json`

Скрипт вызывает только `git` (`diff --name-status -M -z`, `diff --numstat`, `log`) и пишет JSON с ключами в отсортированном порядке. Для каждого пути, изменённого хотя бы с одной стороны:
- `fork`: статус `BASE..FORK` (`A`, `M`, `D` или `R` с исходным путём), число добавленных и удалённых строк, признак двоичного файла;
- `upstream`: то же для `BASE..UP0`;
- `overlap`: `true`, если путь изменён с обеих сторон, включая случай, когда апстрим переместил или удалил файл, который форк менял;
- `lfs`: `true`, если путь в форке подпадает под правило `filter=lfs` из `.gitattributes`.

Отдельные списки в JSON:
- `fork_commits`: коммиты `BASE..FORK` (sha, дата, заголовок, изменённые пути);
- `id_collisions`: пары `#define` с одинаковым числовым значением в `src/data/gfxdata.h` (и других файлах `src/data/*.h`), где одно имя добавил форк, другое — апстрим; например, значение 167;
- `sdl2_in_fork_code`: для каждого файла `src/`, изменённого форком, — число строк в `FORK` с вызовами или типами SDL2, которые в апстриме заменены на SDL3 (список шаблонов — в самом скрипте, источник списка — что апстрим поменял в `BASE..UP0`).

## 2. `docs/upstream/PORT_MAP.md`

Документ пишет sol на основе JSON. Таблица функций форка: список функций взять из `README_AI.md` §1 и сверить с заголовками `fork_commits`; функция, которую нашли в коммитах, но не в `README_AI.md` §1, — отдельной строкой с пометкой. Для каждой функции:
- файлы форка, которые её несут (пути из JSON);
- судьба этих файлов в апстриме: не менялись / изменены / перемещены в `<путь>` / удалены — и куда в `UP0` ушёл код, если удалён (класс или файл);
- тесты форка из `tests/*.cpp`, которые её проверяют (по именам тестов и по тому, какие файлы они включают);
- класс переноса: «копировать как есть» (файлы, которых апстрим не трогал и которые не зависят от изменённых апстримом), «применить заново» (апстрим менял те же файлы, архитектура та же), «переписать под новую архитектуру» (код форка опирается на удалённое или перемещённое апстримом);
- зависимости от других функций форка;
- рекомендованный порядок переноса шагами Б3–Б12 плана.

Отдельные разделы документа:
- данные и паки: какие двоичные паки менялись с обеих сторон (особенно `resources/bin/data/sdl_inter.dat`) и список коллизий ID;
- что из форка аддитивно и переносится копированием (папки `resources/hd`, `tools`, `packaging`, `README_AI.md`, тесты форка и другие, найденные по JSON);
- риски переноса, которые видны по JSON, — каждый с путём файла.

Каждое утверждение о коде — со ссылкой `путь@коммит:строка` или путём файла из JSON. Не уверен — пометка «не проверено».

## Тест

`tools/upstream/tests/test_port_inventory.py` на `unittest`:
1. Скрипт, запущенный во временную папку, выдаёт JSON, побайтно равный закоммиченному.
2. Каждый путь со статусом `overlap: true` в JSON действительно изменён в обоих диапазонах (`git diff --quiet` по пути даёт код 1 для каждого диапазона, или путь перемещён или удалён).
3. Каждый путь файла, упомянутый в `PORT_MAP.md` в обратных кавычках, есть в `FORK` или в `UP0`.

Команда проверки (полная):

```
/srv/dune/venv/bin/python -m unittest discover -s tools/upstream/tests -v
```

## Не трогать

`src/`, `tests/`, `resources/`, `CMakeLists.txt`, существующие файлы `tools/`. Не делать merge, cherry-pick и не переносить код — это следующие шаги.

## Чего задача не делает

Не собирает игру и не запускает тесты C++ (это шаг Б1); не решает за владельца ничего, кроме порядка переноса, который потом утверждает ведущий.
