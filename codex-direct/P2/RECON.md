# Задание P2-R — разведка слоя данных и паков перед переносом

## Цель

Собрать факты, по которым ведущий напишет план шага П2 (перенос слоя данных и паков форка на апстрим). Каждый факт — с путём и строкой (`путь@ревизия:строка`), командой и её выводом. Развилки — с вариантами и рекомендацией.

Разведка ничего не меняет: файлы вне `.tmp/p2r/` не меняются, коммитов нет. Плана и правок не пиши. Сборки, CTest и запуск игры запрещены.

## Рабочая копия и ревизии

- Рабочая копия — `/srv/dune/worktrees/u34`, ветка `codex/p1a`, HEAD `9343cb6b97`. В ней есть объекты всех трёх ревизий и объекты LFS паков форка.
- `BASE` = `e17379ad660fca46859b403a6c3d33ec8d831a40` — общий предок.
- `FORK1` = `9208dcf5a358f40afd95c99480e4e09f781ed566` — форк, релиз `v0.8.0-ru-hd.10`.
- `UP1` = `d06f2fcd2a347182c3774fb96e9a85570405c489` — апстрим.
- Перед командами Git: `export PATH=/srv/dune/tools/git-lfs-3.6.1/usr/bin:$PATH`. Python — `/srv/dune/venv/bin/python`.
- Паки читай модулем `tools/hd_assets.py` рабочей копии.
- Файл пака из ревизии получай одним из двух способов. Если `git show <ревизия>:<путь>` — LFS-указатель, скопируй объект `/srv/dune/worktrees/u63/.git/lfs/objects/<oid[0:2]>/<oid[2:4]>/<oid>` в `.tmp/p2r/packs/<ревизия>/<путь>` и сверь sha256 с `oid`. Иначе запиши вывод `git show <ревизия>:<путь>` в тот же путь. Команды `git checkout` и `git lfs smudge` не используй. Если объекта LFS нет или sha256 не совпадает — блок `Q-P2R-01` и стоп.
- Карта переноса — `docs/upstream/PORT_MAP.md` и `docs/upstream/port_inventory.json` рабочей копии.
- Решения владельца — `docs/decisions.md`, особенно Р34 и Р63.

## Что выяснить

1. **Какие паки грузит игра в `FORK1`.**
   - Файлы паков и секции настроек, которые читает код, — `путь@9208dcf:строка`.
   - Как код обращается к записям: по константе-индексу из `src/data/gfx*.h` или по имени. Перечисли функции поиска по имени (например, для записей `HM_`) и их вызовы.
   - Грузит ли игра классические паки `sdl_data.dat`, `sdl_inter.dat`, `sdl_world.dat`, `sdl_mentat.dat` и `sdl_audio.dat`. Кладут ли их в пакет `.github/workflows/release.yml`, `create_release.sh` и `create_release.bat`.
2. **Какие паки грузит игра в `UP1`.**
   - Класс чтения паков (`cDataPack` или другой), его API, файлы паков и секции настроек — `путь@d06f2fc:строка`.
   - Есть ли в `UP1` поиск записи по имени.
   - Для четырёх конфликтов из `id_collisions` карты (`EXPLOSION_CARRYALL` 167, `BMP_SELECT_HOUSE_SARDAUKAR` 144, `ICON_POWER_LOW` 145, `MENTATS` 51): что это за константа — индекс картинки или число записей, и где `UP1` её использует.
3. **HD4-паки форка по позициям.** Для каждого из четырёх паков `resources/bin/data/sdl_{data,inter,mentat,world}_hd4.dat` ревизии `FORK1`:
   - число записей;
   - для каждого индекса от 0 до наибольшего значения константы соответствующего заголовка в `UP1`: имя записи пака и имя константы `UP1` с этим значением. Сводка: совпадают, различаются, записи нет. Полная таблица — в файл `.tmp/p2r/hd4-positions-<пак>.tsv`;
   - имена записей после последнего индекса `UP1`.
4. **Классика без HD.** Перечисли каждую константу индекса картинки во всех `src/data/gfx*.h` и `src/include/gfx*.h` ревизии `UP1`, для которой в HD4-паке нет записи с тем же именем. У каждой: заголовок, значение, места использования в `UP1`.
5. **Классические паки по записям.** Для каждого `.dat` в `resources/bin/data/`, который изменён в `BASE..FORK1` или в `BASE..UP1` и не является HD4-паком:
   - список записей `BASE`, `FORK1` и `UP1` (индекс, имя, sha256 данных);
   - по каждой записи вид изменения на каждой стороне: без изменений, изменена, добавлена, удалена;
   - коммиты форка, которые меняли этот пак (`git log --format='%h %s' BASE..FORK1 -- <путь>`).
   
   Отдельно — записи, изменённые с обеих сторон. Таблицы — в `.tmp/p2r/classic-<пак>.tsv`.
6. **Чтение HD4-паков кодом `UP1`.**
   - Сравни формат файла пака, который ожидает код чтения `UP1`, с форматом HD4-паков `FORK1`: заголовок, версия, таблица записей, сжатие, формат картинок.
   - Ответ: прочтёт ли код `UP1` эти паки без изменений. Если нет — что именно не совпадает, `путь@ревизия:строка` с обеих сторон.
7. **Код форка для паков, которого нет в `UP1`.** Перечисли функции и классы `FORK1`, которые относятся к загрузке и поиску записей паков (включая поиск `HM_` и загрузку HD4), и для каждого — преемника в `UP1` (`путь@d06f2fc:строка`) или «нет».
8. **Эталон для сравнения паков.** sha256 четырёх HD4-паков в теге `v0.8.0-ru-hd.10` (`git rev-parse v0.8.0-ru-hd.10^{commit}` должен дать `FORK1`) и их число записей.
9. **Развилки.** Для каждой — варианты, чем каждый грозит, и рекомендация:
   - нужно ли трёхстороннее слияние классических паков, если по Р34 игра форка грузит только HD4-паки;
   - как совместить номера HD4-паков с константами `UP1`: перестроить паки под номера `UP1` или искать записи HD по имени;
   - что делать с каждым из четырёх конфликтов;
   - другие развилки, найденные по ходу.

## Сдача

Блок `## DONE-P2R | <время UTC из date -u>`. Полный отчёт — файл `.tmp/p2r/RECON.md`: по пунктам 1–9, факты с `путь@ревизия:строка`, команды и выводы. В блоке сдачи — путь отчёта, по одной-две строки итога на каждый пункт, список файлов `.tmp/p2r/` и `### Не проверено`.

## Организация работы

- **Режим:** «Ведёт sol».
- **Порядок:** пункты 1–8 одновременно по дорожкам ниже → пункт 9 по итогам 1–8 → сдача и стоп.
- **Параллельно:** пункты 1–8 не зависят друг от друга, кроме пункта 4: он опирается на пункт 3.
- **Помощники:** до 3, `gpt-6-luna` `xhigh`, без вложенных.
  - Помощник 1 — пункты 1 и 7.
  - Помощник 2 — пункты 3, 4 и 8.
  - Помощник 3 — пункт 5.
  - Корневая нить делает пункты 2, 6 и 9 и сама проверяет выборкой не меньше трёх фактов каждого помощника.
  - В бриф помощника дословно входят абзац «Комментарии в коде» ниже и запрет писать вне `.tmp/p2r/`.
- **Остановки:** только на `## DONE-P2R` или на вопросе `Q-P2R-NN`.
- **Рамка правок:** только `.tmp/p2r/`. Ничего вне неё не меняй, не коммить.

## Комментарии в коде

Категорически запрещено писать комментарий по принципу «полезен, если верен и относится к делу». По умолчанию комментария нет; он должен доказать право на существование: только неочевидное «почему» — инвариант, причина обхода, ссылка на внешнее ограничение. Пересказ кода, планы и история — нет. Внутренние номера находок, планов и решений (`F7`, `A-11b`, `D88`) в комментарий не писать: суть словами.
