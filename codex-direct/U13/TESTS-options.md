# Задание U13-T — приёмочные тесты раскладки главной страницы окна настроек

Режим: **«План у ревьюера»** (см. «Режимы задания» в конце). Исполнитель: Codex `gpt-6.1-sol` `high`; помощник — субагент `gpt-6-luna` `xhigh`.
Рабочая копия: `/srv/dune/worktrees/u13`, ветка `codex/u13-options`, HEAD — текущий `main` (коммит с этим файлом или новее). Коммитов не делай: ведущий коммитит по списку из сдачи.

## Цель

Приёмочный тест C++ поведения из `codex-direct/U13/LAYOUT.md`: при любом поддерживаемом холсте, в HD и в классике, в меню и в игре ни одна кнопка главной страницы окна настроек не накладывается на другую кнопку или на строку настроек, и всё лежит внутри окна, а окно — внутри холста. Реализации в ветке нет: тест пишется по поведению. На коде `main` тест не собирается (нет поля `window` и новой сигнатуры `create`) — это его красный результат. На верной реализации тест проходит. Каждая неверная реализация из раздела «Неверные реализации» роняет тест.

## Источник истины

- Поведение и формулы — `codex-direct/U13/LAYOUT.md`, разделы «Входы», «Величины», «Результат», «Строки содержимого», «Числа для сверки».
- Холсты — `calculateRenderCanvasSize` и `isManualRenderScaleAvailable` из `src/utils/RenderScale.cpp`, `ManualRenderScales` из `src/utils/RenderScale.hpp:15`; эта задача их не меняет, тест вызывает их, чтобы получить холст.
- Список разрешений — `standardResolutions` в `src/gamestates/cOptionsState.cpp:121–157` (35 разрешений от 800 × 600 до 7680 × 4320); тест держит свою копию списка.
- Стиль и регистрация — существующий `tests/OptionsMenuLayoutTests.cpp` и его цель `options_menu_layout_tests` в `CMakeLists.txt:222–233`.

## Что сделать

Перепиши `tests/OptionsMenuLayoutTests.cpp`; имя исполняемого файла `options_menu_layout_tests` и имя теста CTest `options_menu_layout_geometry` не меняются. В цель `options_menu_layout_tests` добавь `src/utils/RenderScale.cpp`. Это задание — исключение из правила исполнителя «существующие тесты и их ожидания не менять» только для файла `tests/OptionsMenuLayoutTests.cpp`: прежние три вызова `create` с восемью параметрами удаляются вместе с прежней сигнатурой.

**Матрица случаев.** Каждый случай — `(Wc, Hc, bh, hd, playing)`:

- холсты А: для каждого из 35 разрешений списка и каждого масштаба из {0 (автоматический), 100, 125, 150, 175, 200} — холст `calculateRenderCanvasSize(w, h, масштаб)`; ручной масштаб, для которого `isManualRenderScaleAvailable` ложно, пропускается;
- холсты Б: `Wc` из {800, 1067, 2133}, `Hc` — каждое целое от 600 до 1440 включительно;
- `hd` = истина с каждым `bh` от 32 до 42 включительно; `hd` = ложь с каждым `bh` от 16 до 20 включительно;
- `playing` — истина и ложь.

**Проверки.** Каждая проверка — отдельная функция; при провале она печатает в `stderr` строку, которая начинается с имени проверки и содержит случай (`Wc`, `Hc`, `bh`, `hd`, `playing`) и имя поля; программа возвращает 1, если провалилась хоть одна проверка.

| Проверка | Что доказывает |
|---|---|
| `exact` | Для каждого случая матрицы каждое поле результата `create` — `window`, `apply`, `advanced`, `status`, `quit`, `mainMenu`, `back`, `save`, `load`, `missionSelect` — равно прямоугольнику по формулам `LAYOUT.md`. Сравниваются `x`, `y`, ширина и высота. Без `playing` `save`, `load`, `missionSelect` равны `cRectangle()`. |
| `table` | Шесть строк таблицы «Числа для сверки» `LAYOUT.md` — числами, записанными в тесте: `window`, `bottomY` (`y` у `quit`), `upperY` (`y` у `save`), `colW` (ширина `quit`), `lastW` (ширина `back`). |
| `inside` | Для каждого случая: окно внутри холста — `window.x ≥ 0`, `window.x + W ≤ Wc`, `window.y ≥ 4`, `window.y + H ≤ Hc − 4`; каждый прямоугольник кнопки варианта (`apply`, `advanced`, `status`, `quit`, `mainMenu`, `back`, а при `playing` ещё `save`, `load`, `missionSelect`) внутри окна: `x ≥ 0`, `y ≥ 0`, `x + ширина ≤ W`, `y + высота ≤ H`, ширина больше 0. |
| `overlap` | Для каждого случая никакие два прямоугольника из набора не пересекаются: кнопки варианта (как в `inside`) и полосы строк 1–9 `{0, k · (bh + c), W, bh}`; пары «полоса — полоса» не проверяются. Пересечение — своя функция теста по полуоткрытым промежуткам: `a.x < b.x + b.w`, `b.x < a.x + a.w`, `a.y < b.y + b.h`, `b.y < a.y + a.h`. `cRectangle::isOverlapping` не использовать: он проверяет только углы и пропускает крестовое наложение. |

**Эталон не из проверяемого кода.** Ожидания `exact` вычисляет функция теста по формулам `LAYOUT.md`, написанная в тесте заново; вызывать для ожидания `OptionsMenuLayout::create` или другой код `src/gamestates/` нельзя. Проверки `inside` и `overlap` смотрят только на результат `create` и на полосы строк, а не на формулы `LAYOUT.md`: они ловят наложение, даже если ошибка в самих формулах.

## Неверные реализации

Каждая обязана ронять тест; в столбце — проверки, которые обязаны упасть.

| № | Неверная реализация | Обязаны упасть |
|---|---|---|
| 1 | Код ветки `main` без правок | сборка теста |
| 2 | Высота окна прежняя: `H = oldH`; ряды кнопок низа новые | `exact`, `overlap` |
| 3 | Высота окна всегда `Hc − 8` | `exact` |
| 4 | Кнопки низа по одной в ряд, как в `main`, а высота окна — `min(Hc − 8, max(oldH, applyBottom + m + 4 · bh + 3 · g + m))` при `playing` и `min(Hc − 8, max(oldH, applyBottom + m + 2 · bh + g + m))` без него | `exact`, `table` |
| 5 | Нижний ряд в порядке «В главное меню», «Выйти из игры», «Назад» | `exact`, `table` |
| 6 | Последний столбец шириной `colW` вместо `lastW` | `exact`, `table` |
| 7 | Верхний ряд и `n` = 2 и без `playing` | `exact`, `table` |
| 8 | В `required` нет поля `m` между строкой «Применить» и кнопками низа | `exact`, `table` |
| 9 | Зазор между рядами кнопок низа — `m` вместо `g` | `exact`, `table` |
| 10 | Окно не по центру: `window.y = 0` | `exact`, `table`, `inside` |
| 11 | В классике окно считается по формулам HD | `exact`, `table` |

**Прогон неверных реализаций.** Для прогона нужна верная реализация, а писать её в рабочей копии ты не должен. Поэтому: копия рабочей копии в `.tmp/u13t-ref/` без папок `resources/` и `.tmp/`; в копии `src/gamestates/OptionsMenuLayout.hpp` заменён верной реализацией по `LAYOUT.md`; собирается только цель `options_menu_layout_tests` (код игры в копии с новой сигнатурой не собирается, и это не нужно); тест на верной реализации зелёный. Затем каждая неверная реализация 2–11 — одна правка копии заголовка верной реализации, своя папка сборки, прогон, строки провала. Копия и её заголовок в сдачу и в рабочую копию не идут; после прогонов удали копию: `rm -rf` по её буквальному пути.

## Организация работы

- Порядок: чтение `LAYOUT.md`, прежнего теста и рецепта сборки → PLAN → `PLAN-OK-U13-T` → тест и правка `CMakeLists.txt` → прогон на коде ветки → верная реализация в копии и прогон → неверные реализации 2–11 → удаление копии → сумма → сдача `## DONE-U13-T`.
- Параллельно: после `PLAN-OK` верную реализацию в копии и десять копий неверных реализаций готовит субагент, пока ты пишешь тест.
- Помощники: субагент `gpt-6-luna` `xhigh` — копия, верная реализация по `LAYOUT.md`, неверные реализации по таблице, сборки, прогоны и выжимки логов. Сам — PLAN, тест, сверка провалов с таблицей, итоговая сверка с заданием.
- Остановки — блок `## Q-U13-T-NN` и стоп: формулы `LAYOUT.md` спорят друг с другом или с таблицей «Числа для сверки»; верная реализация по `LAYOUT.md` проваливает `inside` или `overlap`; неверная реализация не роняет обязательную проверку; свободного места на `/` меньше 5 ГБ; команда оболочки дважды подряд не завершилась и за 30 минут не дописала ни строки в журнал.
- Рамка правок: `tests/OptionsMenuLayoutTests.cpp`, `CMakeLists.txt` (только список исходников цели `options_menu_layout_tests`), `.tmp/`.
- Журнал: `.tmp/progress-u13t.md`, строка после каждого шага порядка; это имя сильнее имени журнала в правилах исполнителя ниже.
- Коммитов не делай; раздел `### Коммиты` в сдаче: сообщение и список файлов.
- Комментарии в коде. Категорически запрещено писать комментарий по принципу «полезен, если верен и относится к делу». По умолчанию комментария нет; он должен доказать право на существование: только неочевидное «почему» — инвариант, причина обхода, ссылка на внешнее ограничение. Пересказ кода, планы и история — нет. Внутренние номера находок, планов и решений (`F7`, `A-11b`, `D88`) в комментарий не писать: суть словами.
