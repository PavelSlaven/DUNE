## 3. Подход

### 3.1 Юниты — через 3D-модель и скриптовый рендер

Почему: покадровая генерация дала разные кадры для разных направлений и потребовала скриптов-исправлений; у Codex слабое зрение, и проверять 8 × N кадров глазами он не может. С 3D-моделью все направления, корпус и башня, тень и маска получаются из одной геометрии и одной камеры, а правильность геометрии проверяет скрипт.

Конвейер одного юнита:

1. **Концепт.** Codex (генерация изображений) по Sega-спрайту и утверждённому эталону рисует лист видов: сверху, спереди, сбоку, сзади, 3/4. Для юнитов с башней — отдельно корпус без башни и отдельно башня. Лист утверждаешь ты (стиль); соответствие Sega-силуэту проверяет ведущий.
2. **3D.** Tripo (image→3D или multiview→3D) → GLB корпуса и GLB башни. Кто выполняет этот шаг — вопрос В2.
3. **Нормализация** (скрипт Blender): ось «нос» = +X, масштаб под целевую длину из контракта юнита, центр посадочного кольца башни = точка вращения.
4. **Рендер** (скрипт Blender, Cycles на CPU, фиксированные seed, число сэмплов и версия Blender): орто-камера с углом θ из общего файла камеры, 8 азимутов в порядке движка. Проходы:
   - цвет с альфой;
   - тень (shadow catcher, сама модель невидима);
   - маска цвета Дома;
   - служебный проход маркеров (нос, центр кольца башни, точка опоры) — в игру не попадает, по нему скрипт проверяет направления и выравнивание.
   Рендер в 2× размера HD4 → Lanczos в HD4 → Lanczos в HD2.
5. **Сборка паков** — одним сборщиком `tools/units3d/`, который читает только исходники из репозитория.
6. **Проверки** — тесты п. 5.1 → лист для ревью → ведущий (Opus) → ты.

Маска цвета Дома — два варианта, выбор на пилоте по тесту п. 5.1 № 8:
- (1) зоны Дома закрашены в концепте ключевым цветом → текстура Tripo → маска по цвету текстуры в Blender;
- (2) зоны размечаются в Blender выбором граней скриптом по координатам.

Исходники юнита хранятся в репозитории (LFS): лист концепта, GLB, файл камеры, файл света, манифест (ID, размеры, хэши исходников). Атлас всегда пересобирается из них.

### 3.2 Обновление — перенос функций на свежий апстрим, а не один большой merge

Прямой `git merge` даёт не меньше 118 конфликтных файлов, 20 удалённых файлов, код которых надо переносить в новую архитектуру, и миграцию на SDL3 — всё в одном коммите, который невозможно проверить. Рекомендация:

1. На старте закрепить SHA апстрима — `UP0`. Ветка `port/up-<UP0>` создаётся от него.
2. Аддитивное перенести как есть: `resources/hd`, `tools`, файлы `resources/bin`, кроме классических паков, `tests`, `packaging`, `README_AI.md`.
3. Функции форка переносить по одной: отдельная ветка и PR на функцию; тесты форка этой функции — приёмочные; код — под SDL3 и новую архитектуру.
4. Перед слиянием — догоняющий merge апстрима от `UP0` до свежего SHA.
5. Связать историю: `git merge -s ours pavel/main` в ветку порта (старая история остаётся достижимой), затем `main` перематывается вперёд без force-push.
6. Дальше — обычный `git merge` апстрима по твоему запросу, с отчётом `tools/upstream_sync_report.py` (пересечения файлов, коллизии ID, конфликты паков).

### 3.3 Два потока параллельно

- Поток А не трогает C++: только `tools/units3d/`, `resources/hd/units3d/` и пересборка HD-паков.
- Поток Б трогает `src/`, `tests/`, CMake и классические паки.
- Общая точка — бинарный `resources/bin/data/sdl_data_hd4.dat`. Его никто не правит руками и не мержит: при каждом слиянии паки пересобирает скрипт из исходников.
- Если пилоту А понадобится правка движка (например, смещение тени или точка опоры юнита), её делаем только на новой базе после Б, чтобы не переносить дважды.

## 5. Критерии приёмки

### 5.1 Юнит — скриптовые тесты

Пороги ниже — проект; окончательные коридоры (размер, доля маски) фиксирует пилот. Тесты пишет Codex sol до начала работы.

| № | Проверка | Порог |
|---|---|---|
| 1 | Атлас: ширина = 8 × ширина кадра HD4; кадр = классический кадр × 4; число строк — как в контракте; HD2 = Lanczos(HD4) | точное совпадение |
| 2 | Паки: изменены только записи целевого юнита; остальные записи HD4 побайтно прежние; классический `sdl_data.dat` побайтно прежний | 0 лишних изменений |
| 3 | Направления: экранный угол «носа» по маркерам в каждом кадре = ожидаемый для азимута и θ | ±3° |
| 4 | Выравнивание: маркер центра корпуса во всех 8 кадрах в одной точке; центр кольца башни совпадает с центром кольца корпуса во всех 64 сочетаниях направлений | ±1 px HD4 |
| 5 | Поля кадра: непрозрачные пиксели (α > 16) не ближе 2 px к краю кадра | 0 пикселей |
| 6 | Размер: длина корпуса в кадре E — по таблице контракта (цель утверждается на пилоте) | ±5 % |
| 7 | Альфа: нет пикселей с α < 8 и RGB ≠ 0; силуэт корпуса — одна связная область без дыр, кроме перечисленных в манифесте | 0 нарушений |
| 8 | Маска Дома: целиком внутри непрозрачной области; в каждом кадре не пуста; доля от непрозрачной площади — в коридоре пилота | 100 % / коридор |
| 9 | Тень: размер кадра как у атласа; без цветов юнита; направление смещения = направление теней зданий из А1 | ±10° |
| 10 | Единая камера и свет: хэш файлов камеры и света в манифесте юнита равен текущему | равенство |
| 11 | Воспроизводимость: пересборка из репозитория на чистой копии | ≥ 99,9 % пикселей совпадают, разница канала ≤ 2 |
| 12 | Игра: сборка стартует, в `log.txt` нет новых ошибок загрузки; снимки — 4 Дома × 8 направлений движения × вращение башни при 1920×1080, 800×600, 5120×1440 | артефактов нет (ревью п. 5.2) |
