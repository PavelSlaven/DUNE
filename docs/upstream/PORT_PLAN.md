Источник решений:
- Р4 — функции переносятся по одной, история связывается `merge -s ours`, без force-push;
- Р34 — игра грузит только HD4;
- Р63 — волна 4;
- Р64 — исключение для `<cmath>`.

Источник шагов — `docs/PLAN_units_sega_upstream.md` §3.2 (поток Б), проверки — там же, §5.3. Функции, пути, риски и порядок — `docs/upstream/PORT_MAP.md`. Карточка запуска — `codex-direct/launch-card-27.md`: шаги П2–П15 запускаются без новых карточек; смена подхода или рамки — новая карточка.

## 1. Цель и готовность

Перенос готов, когда выполнены все условия:
1. `main` построен на апстриме `UP1` = `d06f2fcd2a347182c3774fb96e9a85570405c489` и догнан до свежего master апстрима (шаг П14). `git merge-base --is-ancestor` истинен и для апстрима, и для `6662b2f4`.
2. Все 23 функции карты перенесены, каждая — своим шагом, своей веткой и своим PR в ветку порта.
3. Выполнены проверки §5.3 № 1–10 плана.
4. Владелец принял новую сборку в игре до перемотки `main`.
5. Выпущен релиз `v0.9.x-ru-hd`. Номер выбирает владелец.

## 2. Ветка порта и сборки

- Ветка порта — `port/up-d06f2fcd` на GitHub. Сейчас это `UP1` плюс скрипт `tools/upstream/build_upstream_linux.sh`.
- У каждого шага своя ветка `codex/pN` от вершины ветки порта и свой PR в ветку порта. Сливает ведущий вручную, после проверок раздела 3.
- `main` до шага П14 получает только документы процесса и карту переноса (Р63). Единственное исключение — Р64.
- **Сборка Linux** — на servak: `DUNE_DEPS_DIR=$PWD/.tmp/deps DUNE_OUT_DIR=$PWD/.tmp/out bash tools/upstream/build_upstream_linux.sh d06f2fcd2a347182c3774fb96e9a85570405c489`, без `--pristine`, потому что на ветке шага есть код форка. Успех: код 0, все тесты CTest проходят, игра доходит до строки перехода в MENU.
- **Сборка Windows** — на ПК (MSYS2 в `C:\msys64`, SDL3). Механику делает субагент Sonnet, логи — в scratchpad. Успех: сборка без ошибок, все тесты CTest проходят, игра доходит до MENU.
- **CI** — workflows апстрима на PR в ветку порта. Проверка `claude-review` падает до решения владельца на шаге П12 (раздел 6); остальные проверки должны пройти. CI берёт файлы без LFS, поэтому тесты, которые читают HD4-паки, в CI пропускаются; они проходят в сборках Linux и Windows.
- **LFS на ветке порта** — только для путей, которые добавляет форк (с П2 — `resources/bin/data/*_hd4.dat` и `resources/bin/data/scenes/hd4/*.dat`). Файлы апстрима остаются обычными файлами git: слияния с апстримом не дают конфликтов «файл против указателя LFS».

## 3. Цикл одного шага

Каждый из шагов П2–П12 и П8а проходит этапы по порядку. «Кто делает» указан у каждого этапа.

| Этап | Что делается | Кто делает | Готово, когда |
|---|---|---|---|

| б. Задание | Требования, рамка правок, список тестов, места остановки с вопросом; проверка `check-literal.py --task` даёт «флагов: 0» | ведущий | задание закоммичено в `codex-direct/PN/` |
| в. Приёмочные тесты | Тесты по описанию поведения из задания: перенесённые тесты форка и новые для SDL3. Тесты фиксируются хэшем, перед заморозкой каждый краснеет по заявленной причине | Codex `gpt-6.1-sol` `high` | тесты закоммичены, лог красного прогона приложен |
| г. Исполнение | Работа test-first по заданию, журнал хода в `.tmp/pN/progress.md`; приёмочные тесты не меняются, правка теста — вопрос | Codex `gpt-6-luna` `xhigh`, основной аккаунт | сдача `DONE` с логами |

| е. Проверка ведущего | Сборка Linux, сборка Windows, тесты, скриптовая сверка рамки правок и чисел, проверка §5.3 № 3: ни один тест форка не удалён, число проверок в тестовом файле не уменьшилось | ведущий; скрипты; субагент Sonnet для Windows | все условия выполнены |

Правила цикла:
- Разведку пропускает только шаг, все факты которого уже собраны в карте и прошлых отчётах. Ведущий записывает это в задание.
- Находки предревью исправляет та же нить исполнителя по ответу ведущего. Исправления проверяют скрипты.
- На каждом запуске: проверка задания `check-literal.py --task` отдельным шагом, ожидатель ответа, надзор раз в 30 минут. Надзор удаляется, когда исполнитель не работает.
- Свободное место на servak — не меньше 5000 МБ, иначе стоп. Временные папки закрытого шага ведущий удаляет только после согласия владельца (список — в отчёте о слиянии).

### Содержание шагов

- **П2 — слой данных и паки.** Разведка `codex-direct/P2/RECON.md` сдана. Задание исполнителю — `codex-direct/P2/TASK.md`, задание на приёмочные тесты — `codex-direct/P2/TASK-T.md`. По отчёту разведки ведущий решает, что остаётся от трёхстороннего слияния классических паков при Р34. Решаются и четыре конфликта номеров из `id_collisions` карты:
  - индекс 167 `sdl_data_hd4.dat`;
  - индексы 144 и 145 `sdl_inter_hd4.dat`;
  - индекс 51 `sdl_mentat_hd4.dat`.
  
  Затем ведущий составляет список «классика без HD» для владельца. Приёмка — §5.3 № 5–7 и тест: код чтения паков `UP1` на SDL3 читает все HD4-паки форка. Эталон сравнения паков по № 5 — тег `v0.8.0-ru-hd.10`, графика закончена (Р63).

- **П3 — загрузка HD4.** Игра `UP1` грузит только HD4-паки (Р34), поиск записей `HM_` и дополнительных записей форка — по имени. Приёмка — тесты функции graphics-modes по карте. Разведки — `codex-direct/P3/RECON.md` и `RECON-2.md`, задание — `codex-direct/P3/TASK.md`, задание на приёмочные тесты — `TASK-T.md`, предревью — `PREREVIEW.md`. Не сделано и перенесено: маски цвета Дома (П6), HD-картинки интерфейса (П4, П5), флаг ветряка и раскладка кадров осадного танка и тени перевозчика (П4), кадры тарелки радара (П8а), глаза и рты ментатов (П11).
- **П4 — HD-рендер и масштаб мира.** Разведка — `codex-direct/P4/RECON.md`. Риски — строки карты о камере (`src/gameobjects/map/cMapCamera.cpp`) и о SDL2-коде. Шаг делится на две части.
  - **П4а.** Задание — `codex-direct/P4/TASK.md`, задание на приёмочные тесты — `TASK-T.md` (`tests/utils/test_HdRender.cpp`, тег `[P4]`). Кадр игры рисуется в цель с плотностью кадра (масштаб показа кадра в окне, округлённый вверх, от 1 до 4), поэтому HD-картинки сохраняют детали в увеличенном окне. Состояние цели рендера SDL3 хранит у каждой цели сам; это проверяет тест вложенной цели. Туман войны с памятью апстрима с HD-рендером не спорит: его текстура получила плотность в П3.

## 7. Организация работы

- **Порядок:** шаги — по таблице раздела 4; внутри шага — этапы а–ж раздела 3.
- **Параллельно:** только шаги из столбца «Параллельно» раздела 4, каждый в своей рабочей копии на servak. Шаги, которые меняют одни и те же файлы, идут по очереди. Порядок их слияния в ветку порта — по номеру шага.
- **Помощники:** задание шага делит механику на независимые дорожки и даёт каждой дорожке одного помощника `gpt-6-luna` `xhigh`. Все дорожки запускаются сразу, одновременно не больше трёх, без вложенных помощников. Корневая нить делает суждение и итоговую сверку.
- **Остановки:** исполнитель останавливается только на сдаче `DONE` и на вопросе `Q`. Ведущий останавливает шаг при свободном месте на servak меньше 5000 МБ, при необратимом действии и при вопросе владельцу из раздела 6.
- **Рамка правок:** задание шага называет файлы. Код вне рамки, приёмочные тесты и `main` до шага П14 исполнитель не меняет.
