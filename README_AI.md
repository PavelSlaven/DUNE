# D2TM v0.8.0 RU/HD — точка входа для AI-агента

Этот файл — актуальный технический паспорт рабочей версии **Dune II — The Maker**. Он предназначен для AI-агента или разработчика, который впервые открывает проект и должен безопасно продолжить работу без восстановления контекста по истории чата.

Upstream-описание находится в [`README.md`](README.md). Пользовательское описание готовой русской сборки — в [`resources/bin/README_RU.txt`](resources/bin/README_RU.txt). Художественные правила HD-ресурсов — в [`resources/hd/STYLE_BIBLE_RU.md`](resources/hd/STYLE_BIBLE_RU.md).

## 1. Что это за проект

D2TM — ремейк **Dune II: The Building of a Dynasty** на C++ и SDL2. Эта рабочая ветка существенно расширяет upstream v0.8.0:

- единая русская/английская сборка с переключением языка;
- режимы графики Classic и HD;
- физический HD-рендер интерфейса и игрового мира;
- единый комплект HD4 с обновлёнными интерфейсом, сценами, зданиями, юнитами и эффектами;
- адаптивные меню и HUD для разрешений от 800×600 до 8K и сверхшироких экранов;
- десять именованных слотов сохранений, быстрое сохранение F5 и загрузка F9;
- пользовательские музыкальные пулы по категориям, история треков и переключение `[` / `]`;
- бронзовая панель быстрых приказов с локализованным текстом и настраиваемыми клавишами;
- отдельная вкладка управления в расширенных настройках;
- восстановленные художественные изображения титров.

Баланс, логика кампаний и числовые ID классических ресурсов должны оставаться совместимыми с исходной игрой, если задача прямо не требует иного.

## 3. Первые действия агента

Перед любым изменением:

1. Прочитать этот файл и относящиеся к задаче исходники/тесты.
2. Выполнить `git status --short`.
3. Считать текущее рабочее дерево ценным и заведомо грязным: в нём много незакоммиченных изменений и новых HD-ресурсов.
4. Не применять `git reset --hard`, `git clean`, массовый checkout или удаление незнакомых файлов.
5. Не редактировать `build-ru\`, `artifacts\` и установленную игру как замену правке исходников.
6. Найти существующий контракт и профильный тест; не создавать параллельную реализацию без необходимости.
7. После правки собрать Release, выполнить профильные тесты и `git diff --check`.
8. Устанавливать результат в папку игры только после успешной проверки и с сохранением пользовательских файлов.

## 4. Технологии и сборка

- язык: C++23;
- система сборки: CMake 3.21+;
- Windows toolchain этой рабочей копии: MinGW-w64 x64 из MSYS2;
- графика/ввод: SDL2;
- шрифты: SDL2_ttf;
- изображения: SDL2_image;
- звук и музыка: SDL2_mixer;
- тесты: небольшие самостоятельные C++-исполняемые файлы, зарегистрированные через CTest;
- ресурсные скрипты: Python, преимущественно Pillow и локальные утилиты.
- крупные бинарные ресурсы: Git LFS; после клонирования требуется `git lfs pull`.

### Получение полной рабочей копии

```powershell
git lfs install
git clone https://github.com/PavelSlaven/DUNE.git
Set-Location DUNE
git lfs pull
```

Без Git LFS в каталоге ресурсов останутся небольшие pointer-файлы вместо
реальных DAT, WAV, PNG и других бинарных данных, и игра/ресурсные скрипты не
будут работать корректно.

`CMakeLists.txt` получает версию из `ENV_D2TM_VERSION`, затем из `GITHUB_SHA`; если обе переменные отсутствуют, версия в интерфейсе будет `unset`.

### Настройка Release на Windows

Из PowerShell в корне проекта:

```powershell
$d2tmToolchain = 'C:\Users\Slaven\Documents\Codex\2026-07-26\new-chat\work\msys64\mingw64\bin'
$env:PATH = "$d2tmToolchain;$env:PATH"
$env:ENV_D2TM_VERSION = '0.8.0-ru-hd'

cmake -S . -B build-ru `
  -G 'MinGW Makefiles' `
  -DCMAKE_BUILD_TYPE=Release `
  -DCMAKE_C_COMPILER="$d2tmToolchain\gcc.exe" `
  -DCMAKE_CXX_COMPILER="$d2tmToolchain\g++.exe" `
  -DCMAKE_MAKE_PROGRAM="$d2tmToolchain\mingw32-make.exe"
```

Существующий `build-ru\CMakeCache.txt` уже настроен на этот toolchain. Переконфигурация нужна после изменения CMake, смены компилятора или очистки build-каталога.

### Сборка


## 7. Архитектура выполнения

Основной поток:

```text
src/main.cpp
  -> loadSettingsFromIni("settings.ini")
  -> разбор аргументов командной строки
  -> cGame::applySettings()
  -> cGame::setupGame()
  -> cGame::run()
  -> cGame::shutdown()
```

`cGame` (`src/cGame.h`, реализация преимущественно в `src/cGame_logic.cpp`) — центральный legacy-координатор. Он владеет состояниями экранов, игровым циклом, SDL-контекстом, менеджерами, звуком, музыкой и переходами. В проекте также остаются глобальные массивы карты, игроков, юнитов, зданий, частиц и снарядов из `src/main.cpp`; любое изменение их жизненного цикла рискованно для сохранений и смены состояний.

## 8. Настройки и локализация

Авторитетная модель настроек — `src/utils/GameSettings.hpp`. Чтение и сохранение INI — `src/utils/common.cpp`. Полное сохранение сохраняет комментарии, порядок и неизвестные ключи существующего файла.

Основные ключи секции `[SETTINGS]`:

| Группа | Ключи |
|---|---|
| Экран | `ScreenWidth`, `ScreenHeight`, `FullScreen`, `RenderScale`, `WorldScale`, `GraphicsMode` |
| Камера | `CameraBorderOrKeyMoveSpeed`, `CameraDragMoveSpeed`, `CameraEdgeMove`, `pauseWhenLosingFocus` |
| Язык | `Language=ru` или `Language=en` |
| Звук | `playMusic`, `playSound` |
| Правила/диагностика | `AllowRepeatingReinforcements`, `AllTurretsDownOnLowPower`, `RocketTurretsDownOnLowPower`, `NoAI`, `oneAi`, `disableWormAi`, `disableReinforcements`, `noAiRest`, `Debug`, `drawUnitDebug`, `drawUsages` |
| Быстрые команды | `KeyAttack`, `KeyRepair`, `KeyUnload`, `KeyDeploy`, `KeyRally`, `KeyRelease` |
| Ресурсы | `GameDir`, `GameRules` |

Значения клавиш сохраняются под именами SDL scancode, например `Left Ctrl`, `R`, `D`. Экран назначения: **Настройки → Дополнительные настройки → Управление**. Код — `src/controls/CommandBindings.hpp` и страница `Controls` в `cOptionsState`.

Локализация устроена без каталога строк:

- короткий UI-текст выбирается через `localization::text(english, russian)` из `src/utils/Localization.hpp`;
- русский контент кампаний — `resources/bin/campaign`, английский — `resources/bin/campaign_en`;
- русские карты схватки — `resources/bin/skirmish`, английские — `resources/bin/skirmish_en`;
- язык применяется при построении экранов; изменение настройки рассчитано на повторное открытие/перезапуск;
- новая надпись не должна запекаться в картинку, если она зависит от языка, клавиши, состояния, цены или прогресса.

## 9. Графика, масштабирование и ресурсы

`GraphicsMode` имеет два значения:

- `Classic` использует классические data pack-файлы;
- `HD` всегда использует единый комплект HD4; разрешение экрана и масштаб мира настраиваются независимо от плотности ресурсов.

Секции ресурсов находятся в `resources/bin/d2tm.cfg`:

- `[DATAFILE]` — Classic;
- `[HD4_DATAFILE]` — HD4.

Основные контейнеры:

```text
data/sdl_data*.dat    — общая графика
data/sdl_inter*.dat   — интерфейс и карточки
data/sdl_world*.dat   — мир, здания, юниты, эффекты
data/sdl_mentat*.dat  — ментаты
data/sdl_audio.dat    — встроенный звук/музыка
data/scenes/hd2|hd4   — внешние HD-сцены
data/hd2|hd4          — отдельные HD UI-текстуры
```

Отдельные UI-текстуры загружаются через `src/utils/HdUiTextureLoader.*` из `data/hd4`. В частности:

- `command_bar.png` — бронзовая панель приказов;
- `credits_team.png` и `credits_title.png` — художественные изображения титров.

Панель приказов рисуется `src/drawers/cCommandBarDrawer.*`; геометрия вынесена в `CommandBarLayout.hpp`. Иконки и рамка являются графикой, а названия приказов и клавиши рисуются поверх динамически. `Move/Идти` использует LMB/ЛКМ; остальные подписи отражают фактические назначения из настроек.

### Правила HD-мастеров

- принятый мастер создаётся в 4× от классического логического размера;
- производные превью меньшего размера могут создаваться через Lanczos, но в поставку входит только HD4;
- ID, число и порядок кадров должны совпадать с классическим контрактом;
- текст, псевдотекст и водяные знаки в мастерах запрещены;
- прозрачные края проверяются отдельно, чтобы не появлялись белые/чёрные ореолы;
- направления юнитов должны соответствовать порядку движка `E, NE, N, NW, W, SW, S, SE`;
- изменение масштаба объекта не должно менять занимаемые клетки, центр регистрации или позицию башни/эффекта.

Подробности и утверждённый визуальный язык: `resources/hd/STYLE_BIBLE_RU.md`. Скрипты в `tools/` делятся на `build_*`, `prepare_*`, `verify_*`, `audit_*` и `fix_*`. Перед запуском скрипта прочитать его входы и выходы: многие рассчитаны на конкретный набор мастеров и могут массово обновлять пакеты.

Формат DataPack описан в `resources/tools/datapack/datapack.md` и `src/utils/cDataPack.hpp`. Порядок файлов и ID — часть runtime-контракта.

## 10. HUD и адаптивные раскладки

Геометрические правила по возможности вынесены в чистые заголовки и покрыты тестами:

- `src/sidebar/HudLayout.hpp`;
- `src/sidebar/MusicControlsLayout.hpp`;
- `src/drawers/CommandBarLayout.hpp`;
- `src/gamestates/OptionsMenuLayout.hpp`;
- `src/gamestates/CampaignMapLayout.hpp`.

При изменении HUD или меню нельзя проверять только 2560×1440. Минимальная ручная матрица:

- 800×600;
- 1024×768;
- 1920×1080;
- 2560×1440;
- 3840×2160;
- сверхширокое разрешение, если затронута горизонтальная раскладка.

Нужно проверять одновременно видимую геометрию, реальные hitbox мыши и возврат из меню по ESC. UI не должен перекрывать поле боя, зоны прокрутки камеры и соседние кнопки.

## 11. Музыка

Музыкальная подсистема:

- `src/audio/MusicPlaylist.*` — shuffle-bag без повторов и история назад/вперёд;
- `src/audio/MusicController.*` — категории, внешние файлы и встроенный fallback;
- `src/audio/MusicTransitionPolicy.hpp` — правило повторного входа в категорию;
- `src/utils/cSoundPlayer.*` — фактическая загрузка и воспроизведение SDL2_mixer;
- `src/managers/cDrawManager.cpp` — кнопки и имя трека на верхней панели карты.

Пользовательские каталоги создаются рядом с EXE:

```text
music/
  gameplay/
  menu/
  conquest/
  briefing/
    atreides/
    harkonnen/
    ordos/
  victory/
  defeat/
```

В этой рабочей копии базовый комплект внешней музыки хранится в
`resources/bin/music`: 22 WAV-файла общим размером 532 834 504 байта. Структура
категорий совпадает с runtime-папкой `music` установленной игры. Этот каталог
является источником для восстановления новой полной установки; `.gitignore`
явно разрешает учитывать WAV-файлы именно из него.

Поддерживаются `.ogg`, `.mp3`, `.wav`, `.flac`, если формат декодируется текущей SDL2_mixer. Если категория содержит хотя бы один рабочий внешний файл, он заменяет встроенный пул этой категории. Повреждённые/неподдерживаемые файлы пропускаются с записью в `log.txt`; если весь внешний пул непригоден, используется встроенная музыка.

Во время миссии:

- `[` — предыдущий реально проигранный трек;
- `]` — следующий трек;
- `M` — музыка вкл/выкл;
- `O` / `P` — громкость вниз/вверх;
- обнаружение противника не должно переключать композицию;
- имя текущего файла показывается между кнопками верхней панели;
- переход между экранами одной и той же категории меню не должен перезапускать интро.

## 12. Сохранения

Основной код — `src/save/`:

- `SaveGameManager.*` захватывает и восстанавливает снимок;
- `SaveFileCodec.*` добавляет заголовок, версию и контрольную сумму;
- `SaveSlotName.hpp` проверяет номера и имена;
- `SaveSlotsDialog.*` реализует UI.

Файлы рядом с EXE:

```text
saves/quicksave.d2s  — слот 1
saves/save02.d2s     — слот 2
...
saves/save10.d2s     — слот 10
```

Запись выполняется через временный файл с последующей безопасной заменой. Максимальный размер — 16 MiB. Не менять формат, порядок сериализации или `FormatVersion` без миграционного решения и обновления тестов.

Сохраняются карта и разведка, игроки, ресурсы, здания, юниты, приказы, очереди, подкрепления и камера. Краткоживущие снаряды/частицы при загрузке очищаются. Сохранение разрешено только во время миссии или из её меню настроек.

## 13. Установка локальной сборки

Перед копированием закрыть игру. Минимальная установка кода — заменить только EXE:

```powershell
$d2tmSource = 'C:\Users\Slaven\Documents\Codex\2026-07-26\new-chat\work\d2tm-v0.8.0-src'
$d2tmInstall = 'C:\Users\Slaven\Desktop\D2TM-v0.8.0.windows.ru'

Copy-Item -LiteralPath "$d2tmSource\build-ru\d2tm.exe" `
  -Destination "$d2tmInstall\d2tm.exe" `
  -Force
```

Если менялись runtime-ресурсы, копировать только соответствующие файлы из `resources\bin\` с сохранением относительного пути.

При создании новой полной установки базовую музыку нужно перенести целиком:

```powershell
$d2tmSource = 'C:\Users\Slaven\Documents\Codex\2026-07-26\new-chat\work\d2tm-v0.8.0-src'
$d2tmInstall = 'C:\Users\Slaven\Desktop\D2TM-v0.8.0.windows.ru'

Copy-Item -LiteralPath "$d2tmSource\resources\bin\music" `
  -Destination $d2tmInstall `
  -Recurse
```

Эта команда предназначена для чистой установки, в которой каталога `music`
ещё нет. При обновлении существующей игры runtime-музыка считается
пользовательскими данными: не применять `-Force` и не перезаписывать её без
отдельного решения.

При обновлении **никогда не перезаписывать без явной необходимости**:

- `settings.ini`;
- `saves\` и legacy-каталог `save\`;
- `music\`;
- `log.txt` (обычно не нужен в пакете);
- пользовательские карты/кампании;
- резервные EXE/INI пользователя.

DLL копируются только если изменился toolchain/runtime или отсутствует нужная библиотека. После установки полезно сравнить SHA-256 исходного `build-ru\d2tm.exe` и установленного `d2tm.exe`.

### GitHub Release

Workflow `.github/workflows/release.yml` запускается тегом `v*` и публикует:

- один общий ZIP с `resources/bin` и `game.ini`;
- Windows x64 ZIP с EXE и всеми найденными MinGW/SDL DLL;
- Linux x64 `tar.gz`;
- macOS Apple Silicon `tar.gz`;
- macOS Intel `tar.gz`.

Платформенный архив и `common-assets` распаковываются в один каталог. Linux
и macOS используют системные SDL2-библиотеки, перечисленные в находящемся
внутри `INSTALL.txt`. macOS-бинарники не подписаны и не нотарифицированы.

Релиз сначала создаётся как draft, платформы собираются параллельно, а
публикация выполняется только после успешной сборки и тестов всех вариантов.

## 14. Диагностика

| Симптом | Куда смотреть сначала |
|---|---|
| Игра не стартует | установленный `log.txt`, наличие SDL DLL и data pack-файлов |
| Неверный язык | `settings.ini: Language`, `Localization.hpp`, соответствующий `campaign*`/`skirmish*` |
| Пропала HD-картинка | `GraphicsMode`, выбранная секция `d2tm.cfg`, файл в `data/hd2|hd4` или data pack |
| Кнопка видна, но не нажимается | чистый layout-контракт и обработчик координат мыши |
| ESC ломает раскладку | `cOptionsState`, `m_prevState`, повторное построение layout после перехода |
| Музыка перезапускается | категория в `cGame_logic.cpp` и `MusicTransitionPolicy.hpp` |
| Кнопки треков не видны | `MusicControlsLayout`, свободная ширина верхней панели, `cDrawManager` |
| Пользовательский трек пропущен | `log.txt`, расширение и SDL2_mixer decoder |
| Сохранение не загружается | заголовок/версия/checksum, лимит размера, `SaveFileCodec` |
| Тест показывает ошибку точки входа DLL | порядок `PATH`, MinGW `libstdc++-6.dll` против Inkscape |

В Release-сборке компилятор также может показывать legacy-предупреждения в старом коде, в частности вокруг небольших C-массивов в `src/ini.cpp`. Не заглушать предупреждения глобально: исправлять только после проверки формата и регрессионного теста.

## 15. Правила безопасных изменений

1. Минимальная правка в существующем потоке предпочтительнее нового параллельного слоя.
2. Новую раскладку сначала выражать чистой геометрией и тестом, затем подключать к SDL-отрисовке/вводу.
3. Динамический текст всегда рисовать движком; не встраивать язык и клавиши в PNG.
4. При смене ресурса сохранять ID, число кадров, направления и точки регистрации.
5. При изменении настроек обновлять чтение, запись, UI и тесты вместе.
6. При изменении сохранений проверять старый файл, повреждённый файл и round-trip.
7. При изменении музыки проверять внешний пул, пустой пул, fallback и повторный вход в ту же категорию.
8. Не считать успешную компиляцию достаточной для UI: обязательна ручная проверка экрана в установленной игре.
9. Не удалять резервные файлы в установленной папке без отдельного запроса пользователя.
10. Не коммитить `build-ru\`, временные изображения, `tmp\`, локальные backup-каталоги и пользовательские данные игры без явного решения.

## 16. Критерии готовности задачи

Задача считается завершённой, когда:

- изменён авторитетный исходник или мастер, а не только установленная копия;
- добавлен/обновлён профильный тест, если логика допускает автоматическую проверку;
- Release собирается;
- профильные тесты проходят с правильным MinGW runtime;
- `git diff --check` не сообщает ошибок;
- проверены затронутые русский и английский варианты;
- для UI проверены минимум 800×600 и 1920×1080, а для HD-плотности — также HD4-сценарий;
- ручной запуск выполнен из установленной папки;
- пользовательские `settings.ini`, `saves\` и `music\` сохранены;
- итоговый отчёт перечисляет фактически выполненные проверки и оставшиеся ограничения.

## 17. Известное состояние рабочей копии

- Репозиторий содержит большой набор незакоммиченных изменений и новых файлов; чистый git baseline отсутствует.
- `build-ru` — актуальный Release x64 build-каталог, но он не является источником истины.
- Базовый runtime-пул из 22 WAV-файлов сохранён в `resources/bin/music`; на 2026-08-04 он побайтово совпадает с установленной папкой `music`.
- При отсутствии `ENV_D2TM_VERSION` интерфейс показывает `version unset`.
- Глобальный Windows `PATH` может подхватить несовместимую DLL Inkscape при запуске тестов.
- Архитектура остаётся legacy: `cGame` и глобальные массивы связывают много подсистем, поэтому широкие рефакторинги требуют особенно тщательной проверки переходов, новой игры и загрузки сохранения.
- `resources/bin/README_RU.txt` подробно описывает пользовательские возможности сборки, но может отставать от нового кода; контракты всегда подтверждать по исходникам и тестам.

Если фактическое состояние расходится с этим документом, сначала подтвердить расхождение кодом, CMake и runtime-файлами, затем обновить `README_AI.md` в той же задаче.
